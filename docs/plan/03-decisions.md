# 設計判断の記録（ADR）

形式: `ADR-NNN タイトル` / 状況 / 判断 / 理由 / 影響。新しい判断は末尾に追記し、既存の ADR は書き換えず「superseded by」を付ける。

## ADR-001 SDK の tool runner を使わず自前ループにする
- 状況: 公式 Python SDK にはツール実行ループを自動化する tool runner（beta、自動圧縮つき）がある
- 判断: 使わない。`client.messages.create` を自前で回す
- 理由: 3.6 の分岐再実行と 4.3 のアブレーションには、ステップ境界で会話と環境を止めてスナップショットを取り、任意のステップから再開する制御が要る。自動圧縮はコンテキスト戦略の比較（4.9）と干渉する
- 影響: `tool_result` ブロックの並び（先頭）、`stop_reason` の扱い、並列ツール呼び出しの実行は自前で正しく扱う

## ADR-002 サンプリング引数を使わず、決定性は record/replay で担保する
- 状況: Sonnet 5 系は `temperature` 等の非デフォルト値で 400 を返す。Haiku 4.5 では設定できるが、設定しても完全な決定性は得られない
- 判断: すべてのモデルでサンプリング引数を設定しない。単体テストと再計算の決定性はカセット再生で得る。live の揺れは反復（pass^k）で扱う
- 影響: 「同一版の 2 回の live 実行が違う」ことは仕様。replay と live の数値を混ぜない来歴ラベルが必須になる

## ADR-003 環境はコーディング環境ではなく合成オフィス環境にする
- 状況: コーディングエージェント環境（git リポジトリ）は現実的だが、1 run が長く高価で、障害やドリフトの注入が難しい
- 判断: SQLite ベースの `office` 環境（予定・メール・ファイル・外部サービス）を作る
- 理由: スナップショットがファイルコピーで済む、状態検査が SQL で書ける、注入器（障害・ノイズ・ドリフト）を環境側に置ける、1 run が短い
- 影響: 現実の複雑さは再現しない。結果ページに「例示環境での検証」と明記する。コーディング環境は将来の拡張（`env/repo.py`）として設計だけ残す

## ADR-004 来歴ラベル live / replay / simulated を数値単位で付ける
- 状況: SPRT の誤り率や選択曲線は Monte Carlo で示せるが、それを「実測」と混同しやすい
- 判断: 結果 JSON の各数値に来歴を付け、結果ページと summary に表示する。混在させた統計量は作らない
- 影響: 実験スクリプトは数値ごとにラベルを持つ。`verify` はラベル無しの数値を拒否する

## ADR-005 計画乖離率の粒度はツール名列で近似する
- 状況: 原典 4.7 は「意味的同値の粒度で取った編集距離」と定義する。意味的同値判定を全ステップに適用するとジャッジ呼び出しが増える
- 判断: 乖離率 δ はツール名列の編集距離で計算し、乖離箇所だけをジャッジで正当性判定する
- 影響: 引数だけが違う逸脱は δ に現れない。限界として結果ページに書く

## ADR-006 本番トラフィックは生成器で代替する
- 状況: 実運用が存在しないため 8章の本番→テスト・分布距離・二重トラックを本物のデータで検証できない
- 判断: `ProdStream` が日別に分布をシフトさせたセッションを生成し、それを v01 で実行した run を「本番」とみなす
- 影響: 来歴は `live (synthetic prod)`。実運用での有効性は本プロジェクトでは主張しない

## ADR-007 合格基準は実装前に固定し、変更は ADR で行う
- 状況: 実験が基準を満たさないとき、基準を緩めるか実装を調整する誘惑が生じる
- 判断: 基準は `02-experiment-catalog.md` と `registry.yaml` に実装前に書き、変更は新しい ADR を伴う。満たさない場合は NEGATIVE として記録する
- 影響: 否定的結果が正当な成果物になる。`summary.md` に NEGATIVE の列を設ける

## ADR-008 live API が使えない環境では決定的シミュレータで軌跡を作る
- 状況: 本セッションでは `ANTHROPIC_API_KEY` がシェルに export されておらず、`AGENTEVAL_BUDGET_USD` も未設定。CLAUDE.md の規則により live 実行は起動しない。しかし 25 実験のうち 11 が live を前提にしている
- 判断: `AGENTEVAL_LLM_MODE=sim` を追加し、`llm/simulator.py` の決定的シミュレート・エージェントで軌跡を作る。挙動は**版の system prompt の section マーカー**から読み取り、タスクの意図は `Task.sim`（acceptance とは独立に書いたフィールド）から取る。誤りは `(task_id, seed, repeat)` に固定した「運」ベクトルから引き、版をまたいで同じ運を使う（対応のある比較になる）
- 理由: (1) 評価手法の実装とその反応を検証するには軌跡さえあればよい。(2) 版の比較を対応のある比較にできるため、少ない反復で版の効果を分離できる。(3) コストが 0 なので反復を増やせる
- 影響:
  - **すべての来歴ラベルが `replay` ではなく `simulated` になる**。結果ページと `summary.md` にそのまま出る
  - シミュレータの方策に埋め込んだ性質（例: v04 が検索を繰り返す）を検出する実験は、**循環的になりうる**。各結果ページの「気づき・限界」にその旨を書く
  - live での再確認は未実施。`docs/results/README.md` に未検証項目として一覧を残す
  - `tests/conftest.py` は規則どおり `AGENTEVAL_LLM_MODE=replay` を強制し、ソケットも塞ぐ。run を作るテストは `LLMClient(mode="sim", simulator=...)` を明示的に組み立てる

## ADR-009 「反転」を対応のある反復の不一致率で定義する
- 状況: 3章の実験は「変更で反転したテスト」を数える。合格率の差で定義すると、反復が少ないときに反復間の揺れが版の効果を覆い隠す。また版ごとに反復数が違うと、同じ「運」を比べていないので偽の反転が出る
- 判断: 反転 = **同じ `(task_id, repeat)` の対**で合否が変わった割合が、そのタスクのフレーク帯（ベースライン版の反復から出した二項の Wald 95% 半幅）を超えること。全版で反復数をそろえる
- 理由: シミュレータは `(task, seed, repeat)` に対して決定的なので、対応のある比較にすれば反復の揺れが相殺され、版の効果だけが残る。「帯の内側の変化は変化と数えない」という `02-experiment-catalog.md` の規定はそのまま適用する
- 影響: 合格率の差だけを見る素朴な定義より反転の検出が鋭くなる。live では同じ `(task, repeat)` でも応答が揺れるので、この定義は sim だからこそ成立する。live で再確認するときは反復数を増やして帯を測り直す必要がある

## ADR-010 sim モードでは反復数を増やす（live の反復数と分ける）
- 状況: `corpus.yaml` の `repeats` は live の予算制約（ベースライン 5、その他 3）で決めてある。sim では API コストが 0 なので、この制約に従う理由が無い
- 判断: `corpus.yaml` に `sim_repeats` を追加し、sim モードでは全版 10 反復にする。live モードでは従来の `repeats` を使う
- 理由: フレーク帯が狭まり、版の効果を分離できる。反復数を版でそろえることは ADR-009 の前提でもある
- 影響: コーパスは 46 タスク × 12 版 × 10 反復 = 5,520 run。生成に約 12 分（並列 4）。`data/` は gitignore なので容量の問題は無い

## ADR-011 live 検証にもとづき環境・規則・シミュレータを直す
- 状況: `.env` の `ANTHROPIC_API_KEY` を使って実 API で実行したところ、sim だけでは観測できない欠陥が 5 件出た（`IMPROVEMENT.md` L1〜L5）
- 判断: 以下を直す。いずれも合格基準は変えず、観測の側を直している
  1. `contacts_search` を 14 個目のツールとして追加する。環境に `contacts` テーブルがあるのに引く手段が無く、宛先が必要なタスクが原理的に解けなかった
  2. `v01_baseline` の `finish_rules` を強化し、文章だけの返答では完了にならないことを明記する。派生 8 版のプロンプトを再生成する
  3. リンターの `claim_done_requires_checks` を `finish` イベント起点から run 全体の判定に変え、`declare_completion_with_finish` を追加する。実エージェントの 8 割は `finish` を呼ばないため、従来の実装は偽陰性を出していた
  4. `env/checks.py` に `normalize_text` を入れ、桁区切りと全角数字を正規化する。受入基準が `1500` を要求し、エージェントが `1,500円` と書いて落ちるのは評価側の欠陥である
  5. シミュレータの `search_before_write` を版によらず True にする。「`workflow` section が無い版は読み取りもしない」というモデル化が live と逆向きの結果を生んでいた（v07: sim 0.30 / live 0.97）
- 理由: 評価手法の検証は、評価対象（エージェント）と評価器（基準・リンター）の両方が妥当であって初めて意味を持つ。live はそのどちらの欠陥も明らかにした
- 影響: 版ハッシュとツール schema が変わるので sim コーパスを作り直した（46 タスク × 12 版 × 10 反復）。全実験を再実行し、E4-4 が PASS → FAIL に変わった（理由は結果ページに記載）。live 検証の記録は `docs/results/LIVE.md`

## ADR-012 live の run を sim コーパスから必ず分離する
- 状況: `data/traces/` に live と sim の両方の `Run` が入る。`load_corpus()` は全件を返すので、実験が live の run を sim の統計に混ぜてしまう経路があった
- 判断: 実験側の入口（`experiments/_common.py` の `corpus()`）で `mode == "sim"` に絞る。live を使う実験（E0-1）は `live__*` の trace を明示的に読む
- 理由: ADR-004（来歴ラベルを数値単位で付ける）は、混ざった入力からは守れない
- 影響: 混在した統計量が作られなくなる。`agenteval verify` は従来どおりラベルの無い数値を拒否する

## ADR-013 モデル指紋の統計量から識別力の無い項を外す
- 状況: `drift/fingerprint.py` の `statistic()` は「応答長の平均差 ＋ 先頭 20 文字の不一致率 ＋ ツール選択分布の差」を足し合わせていた。live で実際に指紋を取ったところ（`IMPROVEMENT.md` R2）、Haiku 4.5 → Sonnet 5 の入替を **p = 0.130 で検知できなかった**（人工分布では p = 0.002 だった）
- 根拠（判定に依存しない観測）:
  - 先頭 20 文字の一致率は**同一モデルを 2 回取った場合でも 0.2**、別モデルでは 0.1。帰無仮説と対立仮説でほぼ同じ値を取る
  - ミニタスク 10 問のツール選択は 8 問が `__no_tool__` に潰れた（実モデルはツールを呼ばず文章で答える。`IMPROVEMENT.md` L1 と同じ現象）
  - 応答長だけを見ると、対照 p = 0.756 / 入替 p = 0.046 と分離する（Mann-Whitney U でも p = 0.038）
- 判断: 応答長分布だけを使う `permutation_test_lengths()` を追加し、live の判定にはこちらを使う。従来の合成統計量 `statistic()` / `permutation_test()` は**削除せず**、結果ページに「改訂前」として併記する
- 理由: 帰無仮説と対立仮説で同じ値を取る項は、順列検定の統計量に入れても信号を薄めるだけである。この判断は検定の合否を見なくても成り立つ
- 影響: **この変更は改訂前の結果（p = 0.130）を見た後に行った**。根拠は判定に依存しないが、読者はその順序を承知して読む必要がある。結果ページと `IMPROVEMENT.md` に明記した。
  E8-6 の合格基準は**緩めていない**。人工分布に対する既存の 2 基準はそのまま残し、live に対する 2 基準（`live_control_p_value >= 0.05`、`live_swap_p_value < 0.05`）を**追加**した（＝判定は厳しくなる）
- 残る限界: 入替の p = 0.046 はプローブ 30 問では 0.05 ぎりぎりである。プローブ数を増やすか、ツールを呼ばせるミニタスクの設計を直さないと安定しない

## ADR-014 冗長性ペナルティの類似度は変更しない（R4 の取り下げ）
- 状況: E3-3 / E3-7 の FAIL の原因を「冗長性ペナルティの類似度がツール名列だけなので、同種タスクが相互に重複と判定される」と診断し、正規化引数を含める改訂（`IMPROVEMENT.md` R4）を計画していた
- 検証: live の軌跡でツール名列の同質性を測ったところ、**診断の前提が成り立たなかった**
  - live（10 タスク）: 異なるタスク間の類似度は平均 0.257、0.8 超は 45 組中 1 組（2%）。10 タスクで 9 種類の相異なるツール名列
  - sim（同じ 10 タスク）: 平均 0.431、0.8 超は 3 組（7%）。全 46 タスクでは **13 種類**しか無く、最大クラスタは 10 タスクが同一列
- 判断: 類似度の定義は**変更しない**。R4 は取り下げる
- 理由: 実エージェントの軌跡はタスクごとに十分ばらけており、冗長性ペナルティは意図どおり「本当に似ているテスト」だけを落とす。潰れているのはシミュレート・エージェントの軌跡の側である
- 影響: E3-3 / E3-7 の FAIL の原因は「手法（類似度の定義）の限界」ではなく「**sim の軌跡の多様性不足**」に訂正する。結果ページの診断を書き直す。live で同じ規模のコーパスを作れば結論が変わりうる（未検証）

## ADR-015 E0-1 の順序一致の基準は「置き換えず、足す」
- 状況: E0-1 の `version_ordering_preserved`（live と sim で版の合格率の順序が一致するか）が未達だった。原因を「同点に近い量の順序を基準にした設計の誤り」と考え、書き直しを計画していた（`IMPROVEMENT.md` R3）
- 検証: live の反復を 3 → 6（各版 n=60）に増やして測り直したところ、比較していた 3 版（v01 / v03 / v07）は**信頼区間が重ならない組が 0 組**だった（95% 区間の半幅 ±0.063）。順序を検証できる版の組がそもそも無かった
- 判断:
  1. 比較対象に v02_dateformat（sim で合格率が明確に下がる版）を加え、順序を検証できる組を作った。結果、分離できる組が 2 組でき、**その組では sim の順序が live と一致した**
  2. `version_ordering_preserved` は**基準として残す**。E0-1 の判定は FAIL のままになる
  3. 統計的に分離できる組に限った `ordering_ok_on_separable_pairs` と、その組数 `n_separable_version_pairs >= 1` を**追加**する
- 理由: 基準を置き換えれば E0-1 は PASS になるが、それは「基準に合うまで弄る」ことになる（CLAUDE.md）。
  ill-posed な基準であることは結果ページに数値付きで書き、判定は厳しい側に倒す
- 影響: E0-1 の criteria は 4 → 6 に増えた（判定は厳しくなる）。判定は FAIL のまま
