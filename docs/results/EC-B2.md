## 方法

### 割り振り
EC-B2P と同じ（位置で課金の種類を決める。M4 の按分。`llm/cost.py` を呼ばない独立実装）。`history_cache: on` の版（c01・c12・c13・c04）では会話履歴の末尾に区切りがあるので、履歴中のブロックは初回 $p_w$、以降 $p_r$ になる（NEW_IDEA 6 章の表）。off の版（c01o と対照 (a) の台本）では接頭辞より後ろはすべて $p_{in}$ である。
system＋ツール定義の接頭辞のトークン数 $P$ は版ごとに一定である。
**改訂（W0-Z、2026-11-07。W1-I1 のレビュー）**: $P$ を on の版のステップ 0 の usage から $T_0 - \text{in}_0$ で求めてはいけない。`history_cache: on` では初回ユーザーメッセージ（user0）の末尾にも区切りが付き、ステップ 0 の `input_tokens` がほぼ 0 になるので、$T_0 - \text{in}_0$ は「system＋ツール定義＋user0」になる。
$P$ は **off の版 `c01o_no_history_cache` の run のステップ 0** から $P = T_0 - \text{in}_0$ で求める（off では接頭辞の区切りより後ろがすべて通常入力なので、$\text{in}_0$ が user0 に等しい）。c01o の run の間で値が一致することを確かめ（一致しなければ `history_cache_prediction_error` が `ValueError` を出す）、同じ $P$ を on の版 c01・c04 の割り振りと H3 に使う。
c01・c04・c01o は system プロンプトとツール定義が同一で、違いは `cache_control` の位置（c04 は加えて出力の上限と詳細度）だけなので $P$ は共通である（W1-I8 は c04 のツール定義が c01 と同一であることを確かめる）。`allocate`・`counterfactual_cost`・`history_cache_prediction_error` にはこの $P$ をキーワード引数 `prefix_tokens` で渡す（SPEC.md 9.1 節）。
なお H2 と対照の CCA（ツール結果のブロックの課金）は、ブロックの位置が $T_0$ から先なので $P$ の取り方に依存しない。$P$ が変えるのは接頭辞と初回ユーザーメッセージの分け方と、H3 の反実仮想だけである

### H2: 詳細出力の帰属
- `core24` の 24 タスクそれぞれで、$D_t = \overline{\mathrm{Cost}}(c04, t) - \overline{\mathrm{Cost}}(c01, t)$、$N_t = \overline{\mathrm{CCA}}_{\text{run\_tests}}(c04, t) - \overline{\mathrm{CCA}}_{\text{run\_tests}}(c01, t)$。c04 側は 3 反復の平均、c01 側はコーパスの 6 反復の平均（ADR-044 (A)。方法の定義は変えず、タスク集合が `sub10` の 10 件から `core24` の 24 件に、c04 の反復が 1 から 3 になった）
- `verbose_attribution_to_run_tests` $= \sum_t N_t / \sum_t D_t$（比の和。タスク単位のクラスタ・ブートストラップで 95% 区間を記録）
- c04 と c01 はどちらも `history_cache: on`（G0 項目 13）なので、詳細出力の再送は初回 $p_w$・以降 $p_r$ で課金される。off の場合よりコスト増 $D_t$ は小さい（n 回再送される出力で約 $(p_w + p_r(n-1))/(p_{in} n)$ 倍、n = 10 で約 0.21 倍）。帰属の比 $N_t / D_t$ の定義は変わらない
- c04 では詳細出力が振る舞い（ステップ数）を変えうるので、$D_t$ には再送以外の増分も入る。比が 1 を超えることも、0.8 を下回ることもありうる。0.8 は「増分の大部分が `run_tests` 出力の生涯コスト」という主張の操作的な定義である

### H3: 履歴キャッシュを外したときのコスト増の予測（主指標は run 内の反実仮想）
G0 項目 13 で c01 系を `history_cache: on` にしたので、植込みは「キャッシュを外した版」`c01o_no_history_cache` になり、予測するのは節約ではなく**コスト増**（on と off の差）である。
on の側の実測はベースライン `c01_baseline` の run から、off の側の実測は植込み `c01o_no_history_cache` の run から取る。

- 各 run j について、**キャッシュ関係の usage の値（`cache_creation` / `cache_read` の履歴部分）を使わず**、総入力の増分 $\Delta_i$ と出力トークン数（と c01o から求めた接頭辞の長さ $P$。初回ユーザーメッセージは $T_0 - P$）だけから 2 通りの費用を計算する
  - $\hat C^{\text{off}}_j$: 同じ軌跡を `history_cache: off` で送った場合（接頭辞より後ろはすべて $p_{in}$）
  - $\hat C^{\text{on}}_j$: 同じ軌跡を `history_cache: on` で送り、位置モデルどおりにキャッシュが効いた場合（各ブロックは初回 $p_w$、以降 $p_r$）
  - 接頭辞（system＋ツール定義）の課金は両者で実測値を共通に使う（直前の run からの経過時間で接頭辞が温かいかが変わるが、差の比較では打ち消す）
- 予測増加 $\hat S_j = \hat C^{\text{off}}_j - \hat C^{\text{on}}_j$（$> 0$）。$L_j$ は台帳の実費
- 残差は、その run が実際に送られた設定の側でだけ取れる
  - on の run の集合 $J_{\text{on}}$ = コーパス（段 `corpus`）の `c01_baseline` の全 run（`core24` × 6 反復 = 144 run）。$r_j = L_j - \hat C^{\text{on}}_j$
  - off の run の集合 $J_{\text{off}}$ = `c01o_no_history_cache` の全 run（`sub10` × 1 = 10 run）。$r_k = L_k - \hat C^{\text{off}}_k$
- 相対残差 $e_{\text{on}} = \sum_{j \in J_{\text{on}}} r_j / \sum_{j \in J_{\text{on}}} \hat S_j$、$e_{\text{off}} = \sum_{k \in J_{\text{off}}} r_k / \sum_{k \in J_{\text{off}}} \hat S_k$
- `history_cache_prediction_error` $= \lvert e_{\text{off}} - e_{\text{on}} \rvert$
- **意味**: ある軌跡を off で送った実費は $\hat C^{\text{off}} + r^{\text{off}}$、on で送った実費は $\hat C^{\text{on}} + r^{\text{on}}$ なので、実際の増加は $\hat S + r^{\text{off}} - r^{\text{on}}$ で、（実際の増加 / 予測増加）− 1 = $(r^{\text{off}} - r^{\text{on}}) / \hat S$ になる。$e_{\text{off}}$ と $e_{\text{on}}$ はこの 2 項を、それぞれの run 群で予測増加に対する比として推定したものである。
  旧定義（c01h の run だけで $\lvert \sum S_j - \sum \hat S_j \rvert / \sum \hat S_j$、$S_j = \hat C^{\text{off}}_j - L_j$）は $\lvert e_{\text{on}} \rvert$ に等しく、$e_{\text{off}} = 0$ を仮定したものに当たる。新しい定義はその仮定も off の版の実測で検査する
- **情報の大半は $e_{\text{on}}$ が持つ**: off では接頭辞より後ろがすべて $p_{in}$ で、接頭辞は実測を共通に使うので、位置モデルどおりなら $e_{\text{off}}$ は 0 になる。0 から外れるのは、off の版で接頭辞より後ろにキャッシュが効いている（区切りが残っている。実装の誤り）か、$\Delta$ の数え方の誤りである。$e_{\text{on}}$ と $e_{\text{off}}$ を個別に結果に書く
- **$J_{\text{on}}$ をコーパスの c01 の全 run にする理由**: on で走るのはベースラインなので run 数が多く（144）、$e_{\text{on}}$ が安定する（G0 項目 13 の「検出力はむしろ上がる」）。集合はデータを見る前に固定する。
  記録のみ: `sub10` のタスクに限った $e_{\text{on}}$（c01 の 60 run。c01o とタスクを揃えた感度分析）、版ごとの $e_{\text{on}}$（c12・c13・c04 も on なので同じ式が当たる。ただし c12・c13 は system プロンプトが c01 と違うので c01o の $P$ は使えない。$P$ の求め方は W0-Z の未決 6 で決めた（TASK.md の申し送り表）: $P$ は c01o から求め、ツール定義と system が c01 と同じ c04 にだけ使う。**c12・c13 の版ごとの $e_{\text{on}}$ は「該当なし」と記録する**（W2-A1 で反映。データを見る前の決定））
- **自明でないこと**: 予測にキャッシュ関係の usage を使うと、予測と実測は同じ値の言い換えになり一致は自明になる。使わないので、実際のキャッシュが位置モデルどおりに働かない場合（最小キャッシュ長、区切りの数の上限 4、区切りから遡って探す範囲の上限、有効期限 5 分、キャッシュの取りこぼし）に $e_{\text{on}}$ の誤差として現れる。予測が外れた run は `cache_creation` / `cache_read` が 0 かどうかで原因を切り分けて記録する
- **なぜ run 内の反実仮想を主にするか**: c01o と c01 はモデルへの入力が同一で、違いは `cache_control` の位置だけである（モデルの振る舞いは変わらない）。したがって一方の軌跡は他方でも同じ確率で起こり、「同じ軌跡をもう一方の設定で送った費用」は正当な反実仮想になる。版の間の費用差（c01o の 10 run の平均 対 `sub10` の c01 の 60 run の平均）は同じ期待値を持つが、軌跡の揺れで汚れる。これを `history_cache_increase_between_versions` として 95% 区間付きで記録し、**事前予測**（W3-A2 が c01 パイロットの軌跡に $\hat S$ の式を当てて G2 の前に固定する予測増加率 $\sum \hat S / \sum \hat C^{\text{on}}$）と並べる（記録のみ）。版間の比較を基準にしない理由は下記の検出力の計算による

### 対照 (a): 帰属が生涯（再送回数）を反映すること
- スクリプト化エージェントの対: どちらも同じタスク、同じ 12 ツールステップ＋`finish`、同じ詳細出力 1 回。E 版はステップ 1 で、L 版は最後のツールステップ（ステップ 11）で詳細出力を出す。`history_cache: off`（G0 項目 13 で c01 が on になったので、台本は `c01o_no_history_cache` のハーネスを借りる。`Run.version_id` は `c01o_no_history_cache`。SPEC.md 11.5 節）。台本は W1-I8 が実験スクリプトの中で組む（SPEC.md 11.5 節。段 `offline`）
- `control_attribution` $= \mathrm{CCA}_L(\text{詳細出力}) / \mathrm{CCA}_E(\text{詳細出力})$。位置モデルの予測は $n_L / n_E = 1/11 \approx 0.091$
- **意味**: 出力の大きさ $\tau_i$ だけで帰属する実装（再送回数を見ない）は比が 1.0 になって落ちる。CCA が「生涯コスト」になっていることの検査である。算術でほぼ決まるので、来歴は simulated、検査としては実装の正しさの確認に近い（「気づき・限界」に書く）
- `history_cache: on` では予測比が $p_w / (p_w + 10 p_r) = 1.25 / 2.25 \approx 0.56$ になり基準を満たさない。対照は off で行う

### 対照 (b): c12_null（記録のみ）
c12 − c01 の `run_tests` 帰属の差を 95% 区間付きで記録する。「差が無い」ことを基準にすると、検出力が低いほど通りやすい（区間が広いほど 0 を含む）ので、同等性の幅を決めずに基準にはしない。W3-A2 で、同等性の幅 = MDE とした同等性検定（TOST）を基準に足すかを判断する。

### パイロットで計算する量（W3-A2）
パイロットは c01 だけ（48 タスク × 2 反復、`history_cache: on`）なので、c04・c01o の値は見ない。次を計算して基準を確定する。
**パイロットの run では H3 の残差 $r_j$ と $e_{\text{on}}$ を計算しない**（c01 が on になったので計算できてしまうが、基準を確定する前に指標そのものを見ることになる）。キャッシュ関係の usage はパイロットでは下表の「履歴キャッシュの作動」の数え上げにだけ使う。

| 量 | 計算 | 何に使うか |
|---|---|---|
| 1 run の費用の反復間 SD $\sigma_c$ | $\hat\sigma_c^2 = \frac{1}{2T}\sum_t (x_{t1} - x_{t2})^2$（同じタスクの 2 反復の差） | H2 の分母の揺れ |
| `run_tests` 出力の切り詰め前後の大きさ | 実行器が記録する切り詰め前の文字数 `raw_chars` と表示した文字数 `shown_chars`（SPEC.md への要望）、トークン換算は c01 の usage から得る文字/トークン比 | c04 の予測コスト増 $\hat D_t = \sum_{\text{run\_tests}} (\text{raw} - \text{shown})_{\text{tok}} \cdot \big(p_w + p_r (n_i - 1)\big)$（c04 は on。G0 項目 13 の前は $n_i \cdot p_{in}$ だった） |
| H2 の検出力 | $\sum_t \hat D_t \ge 2.8 \cdot \sigma_c \sqrt{10 \cdot (1 + 1/6)}$ を満たすか（両側 5%、検出力 80%。W3-A2 の時点の計画 `sub10` × 1 の式。ADR-044 (A) の後は $\sqrt{24(1/3 + 1/6)}$） | 満たさなければ c04 のタスク数・反復を増やす案を G2 に出す（ADR） |
| H2 の比の区間幅の見込み | デルタ法 $\mathrm{SE}(A) \approx \sqrt{\sum_t (N_t - A D_t)^2} / \lvert\sum_t D_t\rvert$ に、$N_t, D_t$ の揺れとして c01 の反復間 SD を当てた保守的な値 | 0.8 という閾値と区間幅の比較。区間幅が 0.2 を超えるなら基準を「区間の下限 ≥ 0.6」等に置き換える案を ADR で出す |
| 履歴キャッシュを外したときの予測増加の大きさ | c01 パイロットの軌跡に $\hat S$ の式を当てる（$\hat C^{\text{off}}$・$\hat C^{\text{on}}$ だけ。実費 $L_j$ と比べない） | 分母 $\sum_j \hat S_j$ が小さすぎて相対誤差が不安定にならないか（1 run あたり予測増加が 0.005 USD 未満なら注意）。予測増加率 $\sum \hat S / \sum \hat C^{\text{on}}$ を事前予測として固定する |
| 版間比較の検出力（記録用） | 予測増加率 / （$\sigma_c$ / 平均費用 × $\sqrt{1/10 + 1/60}$） | 版間比較を基準にしない理由の数値。増加率は旧案の節約率より大きい（同じ仮定で off は on の約 2.2 倍）ので検出力が足りる可能性がある。足りても基準に足すかは G2 で ADR を書いて判断する（記録のみのまま進めてよい） |
| 履歴キャッシュの作動 | パイロットの c01 の run のうち、2 ステップ目以降で履歴部分の `cache_read` が 0 の run の数（残差は計算しない） | 実装の確認（W4-OB と同じ数え上げ）。多ければ G2 の前に実装を直す |
