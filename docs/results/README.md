# 検証結果の読み方と総括

*English: [README.en.md](README.en.md)*

レポート『AIエージェントで見落とされがちな評価手法』の 3章（PTS）・4章（過程・計画の評価）・
8章（テストの陳腐化対策）を、自作の小さなエージェントと環境の上で実装し、
「植え込んだ欠陥に反応し、対照には反応しない」ことを数値で確かめた記録である。

判定の一覧は [summary.md](summary.md)（`uv run agenteval verify` の生成物）。
各実験の 5 項目・方法・数値・判定は `E*.md` にある。
**2026-09-19 にコードと実験設計の全面レビューを行い、評価器側の欠陥 8 件を直して全 27 実験を
再実行した。**その記録は [`REVIEW.md`](../REVIEW.md) にある。
**2026-09-20〜21 に 3章（PTS）を作り直し、実験を 3 件足して 30 件にした。**
合成変更 65 件で学習データを作り（原典 3.8 のコールドスタート）、
**変更履歴・テスト履歴を台帳として記録してラグと変更量を特徴量に入れた**。
これにより逃走欠陥率がランダムの 0.868 倍 → **0.319 倍**、
予算 30% の回帰の再現率が 0.535 → **0.819** になった。記録は [`PTS.md`](../PTS.md)。

## まず読むべき注意（来歴）

**28 実験の数値の来歴は `simulated`（E8-8 のみ `unit`）で、`live` は E0-1 と E0-2 の 2 件だけである。**
軌跡は決定的なシミュレート・エージェント（`src/agenteval/llm/simulator.py`、ADR-008）で作っている。

ただし **sim の妥当性そのものは live（実 API）で 2 回検証した**
→ [LIVE.md](LIVE.md)（第 1 次）、[LIVE2.md](LIVE2.md)（第 2 次）、[E0-1](E0-1.md)、[E0-2](E0-2.md)。
その検証で欠陥が見つかり、修正したうえで全実験を取り直している
（詳細は [`IMPROVEMENT.md`](../IMPROVEMENT.md)）。要点:

- sim が live と**一致する**量: 合否（一致率 0.82）、ステップ数、検証行動率、重複呼び出し率、
  **停止適切性**（live 0.496 / sim 0.500）、**未達での完了宣言**（live 0.471 / sim 0.450）
- sim が live と**一致しない**量: `finish_called`（live 0.683 / sim 1.000）。
  実エージェントは `finish` を呼ばずに文章で終えることがある。
  **`finish` の呼び出しに依存する指標（claims、自己申告忠実度）を sim の数値で語ってはいけない**
- **訂正**: 改訂前は「sim は停止適切性を再現できない（sim 1.0 / live 0.66）」と書いていた。
  これは**測定の誤り**だった。停止適切性を原典 4.2 の定義（未達完了宣言・達成後継続）で測り直すと
  live と sim は一致する。改訂前の実装は「最後のツール呼び出しが `finish` か」しか見ていなかった（ADR-019）
- live 検証前の sim は、植込み版 v07 の効果を**逆向きに**誤っていた（sim 0.30 / live 0.97）
- 植込み版 v02_dateformat の欠陥は**実モデルでは再現していなかった**（実モデルはシステムプロンプトと
  ツール定義が食い違うとツール定義を優先する）。プロンプトを立て直して live で再現を確認した
- 決定的代替判定器は live の Sonnet 5 ジャッジと**一致しない**（±1 以内 0.683、完全一致 0.35）。
  代替判定器は一貫して甘い。ジャッジを使う実験の**スコアの絶対水準**は sim では語れない（[E0-2](E0-2.md)）
- **sim は実モデルより厳しい**。合格率の水準が live より 0.18 低い（E0-1 の `pass_rate_gap`）

シミュレート・エージェントは、
- 挙動を**版の system prompt の section マーカー**から読み取り（LLM がプロンプトに従う経路の代替）、
- タスクの意図を `Task.sim`（acceptance とは独立に書いたフィールド）から取り、
- 誤りを `(task_id, seed, repeat)` に固定した「運」から引く（版をまたいで同じ運を使う＝対応のある比較）

という作りである。したがって、**「シミュレータの方策に埋め込んだ性質を、その性質を測る指標が検出した」
という循環になりうる実験がある**。各結果ページの「気づき・限界」に、どこが循環でどこが循環でないかを
個別に書いた。循環の度合いは実験ごとに違う:

| 循環の度合い | 例 | 読み方 |
|---|---|---|
| 強い（構造的に当然） | E4-1（v04 は検索を繰り返す方策）、E8-6 の人工分布、E8-9 の gap | 手法の「実装が動くこと」しか示していない |
| 中くらい | E8-4（κ の低下）、E8-5（要因帰属） | 機構は本物（外部サービスのキー名変更が合否を変える）だが、大きさは設定次第 |
| 弱い（結果が事前に読めない） | E3-1 / E3-3 / E3-7（選択の逃走欠陥率）、E3-5（節約率）、E3-6（SPRT の試行数）、E8-3（弁別力）、E4-2（無駄呼び出し率） | 実装した手法の性質が数値に出ている。否定的結果もここから出た |

## 否定的結果（NEGATIVE）6 件

### E3-3 不確実性駆動の選択はランダムに勝てない ／ ただし校正は成立する

レビューで 2 つの欠陥を直したうえでの結果である（[`REVIEW.md`](../REVIEW.md)）。
(1) 逃走欠陥率の `F_full` を原典どおり「フル実行で見つかった失敗」に戻した（ADR-018）。
(2) 対照（ランダム・直近失敗優先）にも不可侵集合を含めた（ADR-020）。

**成立した側**: `expected_escape` と実測を同じ量でそろえると校正誤差は **0.080**（基準 0.15）。
選択器は「自分がどれだけ失敗を見逃すか」を正しく見積もれている。
改訂前の 0.325 は、失敗の予測と反転の実測を引き算していたことによる見かけの誤差だった。

**成立しなかった側**: 逃走欠陥率は 0.778 で、ランダムの 0.737 より**悪い**（比 1.056、基準 0.5）。
反転ベースの KPI で測っても比は 1.137 でやはり劣る。予算内の下限（オラクル）は 0.155 なので、
基準自体は達成不能ではない。

方策を 5 通り並べて切り分けた（ランダムに対する比。1 未満ならランダムより良い）:

| 方策 | 失敗 KPI 比 | 反転 KPI 比 |
|---|---|---|
| 原典どおり（カバレッジ優先 ＋ 冗長性） | 1.056 | 1.137 |
| 冗長性ペナルティを外す | 0.948 | 0.622 |
| `H(p̂)/c` だけ | 1.010 | 0.973 |
| 失敗確率 `(1−p̂)/c` | 0.760 | 0.797 |
| **カバレッジ重なりだけ** | 0.839 | **0.344** |

**含意**: この環境で信号を持っているのは原典 3.2（カバレッジ）であって、3.4 の不確実性ではない。
理論的にも整合する。Escape は失敗確率の高いテストを選ぶと最小化されるが、`H(p̂)` は `p̂ = 0.5` で
最大になり、**ほぼ確実に落ちるテスト（`p̂ → 0`）を優先しない**。
**情報利得の最大化（3.4 の目的関数）と逃走欠陥率の最小化（3.8 の KPI）は別の最適化問題であり、
片方を最適化してももう片方は最適化されない。**原典は両者を「選択器の KPI」として同じ章に並べている。

### E3-5 分岐再実行の節約は成立しなかった
`outcome.passed` の一致率は 1.0（60 組）、自己分岐の課金ステップは 0 で、**手法の正しさは成立した**。
成立しなかったのは節約の側で、v02 の live ステップ比は 1.000（通常実行と同じ）。
二重課金を直して 1.113 から下がったが、基準 0.6 には遠い（ADR-021）。
原因は構造的である: 接頭辞を辿り直すには 1 ステップにつき 1 回の「判断確認」呼び出しが要り、
版が変われば必ず課金される。分岐が早いほど「確認のぶんだけ損」になる。
トークン比は 1.024 とステップ比より低く、接頭辞キャッシュの効果はトークン側にだけ現れた。
**含意**: 原典 3.6 は「実行コストは軌跡長 L から接尾辞長 L − i* に落ちる」と書いているが、
**この確認コストが勘定に入っていない**。節約はステップ数ではなくトークン単価で語るべきで、
しかも分岐が遅い（軌跡の後半で初めて差が出る）変更に限られる。

### E3-7 選択の骨格は成立、逃走欠陥率は届かない
不可侵集合は予算 5% でも 100% 選択され、ε-探索は毎回 2 件を混ぜ、予算 100% では逃走欠陥率 0 になる。
**手法の骨格は成立している。**成立しなかったのは「予算 40% で逃走欠陥率 ≤ 0.1」という選択性能で、
実測 0.479。各反復の `F_full` を事前に知っているオラクルは同じ予算で 0.031 まで下げられるので、
**基準は達成不能ではない。届かないのは選択の側である。**原因は E3-3 と同じ。

### E8-3 成果物だけの弁別力は過程の劣化を弁別できない
自明タスクの飽和判定（|d| = 0、飽和 = 真、ライフサイクルへの通知）は成立。
成立しなかったのは境界タスクの弁別力で、0.068（基準 0.3）。
原因は、bad ラベルの版のうち v03_noverify（検査せずに完了宣言）と v04_loopy（重複呼び出し）が
**合格率をまったく下げない**こと。`d(t)` は合否だけで good / bad を分離する指標なので、
成果物が同じで過程が劣化した版は原理的に弁別できない。
**含意**: 8.4 の弁別力は、過程指標（リンター違反率・検証行動率）に対しても定義する必要がある。
これは 4.1 の「成果と過程は独立の軸」という主張の、テスト品質側からの裏返しになっている。

### E3-9 探索が校正を保つかは、この規模では判定できない
原典 3.8 は ε-探索に「選択器の校正を保つ」という役割を与えている。部分観測で 37 件の変更を
逐次処理して測った。**最初の実装は並び順を 1 通りしか試しておらず、校正の改善が +0.006 と出ていた。**
並び順を 5 通りに増やして対応のある比較にすると **−0.0023（対応差の SD 0.0088）** となり、効果は消えた。
検出力の計算では、この効果量を拾うには並び順が **113 本**要る（逃走欠陥率のほうは 407 本）。
**含意**: この実験は「探索に効果が無い」ことを示したのではなく、**5 本の並び順では見えない大きさである**
ことを示した。ただし探索の費用は基準内（0.049、利得 0.058）で、
「探索は当該ラウンドの性能を大きく犠牲にする」という懸念は否定できた。
副次的に、**全件観測の後半 Brier（0.088）が部分観測 ε=0（0.068）より悪い**という観測も得た。
上限として置いた対照が上限になっていなかった。詳細は [PTS.md](../PTS.md)。

### E0-2 決定的代替判定器は live ジャッジと一致しない
仮説の後半は強く成立した。live の Sonnet 5 ジャッジは安定しており（再判定一致 ±1 以内 1.000、
完全一致 0.967）、変異ステップを正しく下げる（0.989）。
成立しなかったのは前半で、代替判定器との一致は ±1 以内 0.683（基準 0.7）、完全一致は 0.35 しかない。
不一致は一方向である。**代替判定器は一貫して甘い**（誤ツール変異で live 1.73 に対し代替 4.00）。
`offline_step_judge` は「期待ツール集合に無い かつ 読み取り系でもない」ときだけ減点するので、
読み取り系ツールへの誤置換をほとんど罰しない。
**含意**: E4-5 の結論の向き（変異ステップは低く評価される）は live でも成立するが、
代替判定器が出す**スコアの絶対水準**は信用できない。

| E3-10 | history_feature_gain −0.075（>0）、beats_coverage_baseline 0（==1） | 履歴の長さ不足 | 他の 3 基準は達成（AUC 0.761 / 再現率 0.810 / 学習が積み上がる）。**ラグ特徴だけなら AUC 0.878 で両方満たす**が、群の取捨を内側検証に任せると選びきれない。内側検証の窓に入る陽性が少なすぎる（[PTS.md](../PTS.md)） |
| E4-2 | waste_rate_diff 0.024（≥0.15）、surrogate_precision 0.16（≥0.7） | 実験設計（天井効果） | 環境のエージェントが checks_run → 修復ループを持つため、結果を消しても最終的に通る。U が v01 でも 0.889 に張り付く。修復ループを持たない版でも測る |
| E4-4 | spearman_rho −0.272（≥0.6） | サンプル数の不足 | カタログが指定する 4 版では順位相関が定まらない（p = 0.728）。全 12 版なら ρ = 0.630（p = 0.028）で関係自体は成立。合成軌跡の順序判定は通っている |
| E4-6 | delta_gap 0.197（≥0.2） | 指標設計 | 対照 v01p の δ が 0 でない（edge タスクでは計画どおりに進まないのが正しい挙動）。正当な逸脱を δ から差し引く |
| E4-7 | auc_gain_v08 0.0（≥0.1） | 実験設計 | niah タスクが 2〜3 ステップしかなく、要約戦略（`summarize_after = 2`）が発火しない。多段の niah タスクを作る |
| E8-7 | stratified_lift 1.889（≥3.0） | **基準が達成不能** | 一様サンプリングでも 45% が重要セッションなので lift の上限は 2.2。層化は採取率を 0.45→0.85 に上げている。基準を lift ではなく採取率の絶対値で書く（ADR が要る） |

**基準はひとつも緩めていない**（ADR-007）。上の「修正案」はいずれも未適用で、適用するなら ADR が要る。

計算であって基準ではない**（[`REVIEW.md`](../REVIEW.md) の §0）。

## 本プロジェクトの限界

1. **個々の実験は live で取り直していない**。live で検証したのは sim の妥当性（E0-1）とジャッジ（E0-2）までで、
   残る 28 実験の数値は sim のままである。LLM の意味理解に依存する部分（意味的影響推定のタグ列挙、
   ジャッジのルーブリック判定、参照方策、汚染時の記憶再生）は決定的な代替で置き換えており、
   これらが示したのは「配管が通っていること」までである。
2. **例示環境である**。SQLite のオフィス環境、14 ツール、46 タスク。実際のコーディング環境や
   長期運用の複雑さは再現していない（ADR-003）。
3. **本番トラフィックは生成物**（ADR-006）。8章の分布距離・本番→テストの結果に「実運用で検証した」
   という意味は無い。
4. **ジャッジ交代時の再判定を検証していない**。E0-2 で live ジャッジの安定性は測ったが、
   モデルを替えたときの再判定（規則が要求している）は検証していない。
5. **タスク集合が同質**。ツール名列が 13 種類しかないため、類似度ベースの冗長性判定が機能しない。
   E3-3 の切り分けでは、冗長性を外すと反転 KPI が 1.137 → 0.622 に改善することを確認した。
6. **シミュレータの方策が結果を決めている実験がある**。上の「循環の度合い」の表を参照。
7. **PTS は変更履歴・テスト履歴の記録が前提である**。履歴が無い状態では学習は依存グラフに負けるが、
   台帳を作ってラグと変更量を入れると逃走欠陥率がランダムの 0.319 倍になる。
   ただし変更 65 件・陽性 122 件は産業用 PTS（数十万コミット）の桁違いに手前で、
   特徴群の取捨を内側検証に任せられるだけの履歴が無い（[PTS.md](../PTS.md)）。
8. **評価器自身の欠陥は、コードを読まないと見つからない**。live 検証で 3 件、2026-09-19 のレビューで
   8 件、2026-09-20〜21 の PTS 作り直しでさらに 5 件見つかった。
   どれも「実験が通っているか」を見ているだけでは見つからなかった。

## 次にやるなら（拡張案）

1. **live での再確認を、否定的結果に絞って行う**。優先度は E3-3 / E3-7（選択がランダムに勝てるか）
   > E3-5（節約率）> E8-3（弁別力）。E0-1 の実測（1 run あたり約 0.007 USD）から、
   46 タスク規模の live コーパスで約 25 USD と見積もれる。
2. **タスクのツール列を多様にする**（E3-3 の切り分けで、冗長性ペナルティが信号を消していることが
   はっきりした。原因は類似度の定義ではなく sim の軌跡の単調さである）。
3. **過程指標に対する弁別力 `d_process(t)` を定義する**（E8-3 の含意）。リンター違反率と検証行動率で
   good / bad を分離できるかを測る。
4. **選択器の目的関数を KPI に合わせる**（E3-3 の含意）。逃走欠陥率を下げたいなら `H(p̂)` ではなく
   失敗確率 `(1−p̂)` で並べるべきで、原典 3.4 と 3.8 の不整合として記録する。
5. **多段の niah タスクを作る**（E4-7）。要約戦略の比較が成立する長さにする。
