# E3-5 Prefix cache and branch re-execution

*日本語版: [E3-5.md](E3-5.md)*

## The five items
- Hypothesis: Branch re-execution agrees with normal execution on outcomes and greatly reduces live steps for small changes. The larger the change, the earlier it diverges
- Planted condition: Branch-re-execute v02 (small change) and v09 (model swap) from v01's trajectories
- Control: Self-branching v01 → v01. It hits the cassette / identical policy, so it never diverges and uses 0 live steps
- Pass criteria: outcome_agreement >= 0.8, live_step_ratio_v02 <= 0.6, divergence_order_ok == 1, self_branch_live_steps == 0
- Provenance: simulated

## Method
Taking a v01_baseline run (repeat=0, whose snapshots are stored) as the base, we retraced the
prefix under a new version (v02_dateformat / v09_model_swap / v01_baseline itself).
At each step the old trajectory's conversation is handed to the new version and the returned
action is compared with the old one through `normalize_args`. On a match we continue; on a
mismatch we record `divergence_step`, restore that step's snapshot, and run to the end with the
normal loop (report 3.6).
The billed step count `live_steps` is the number of decision confirmations whose request does
not exactly match the old version (i.e. confirmation calls when the version hash differs) plus
the number of execution steps after divergence. If the version hash is the same, the cassette
hits and it counts as 0. Validity was checked by comparing `outcome.passed` against a normal
run of the same (task, version).

## Findings and limitations
- Divergence points: v02=[1, 1, 1, 1, 1, 1, 1, 1, 1], v09=[2, 1, 1, 2]
- Self-branch (v01→v01) divergences: 0 (0 is the expected value)
- In sim mode the response to a given version is deterministic, so a self-branch always matches. Under live the response varies even for the same version, so self-branch agreement could fall below 1.0. That is a limitation of sim and needs re-confirmation under live.
- The hypothesis that the median divergence point of the model swap (v09) is smaller than v02's must be read together with the counts, because the median is undefined when no divergence occurs.
- **Correction under ADR-021**: the pre-revision code counted the decision confirmation at the divergent step as billable and then re-sent that same step to the model (`resume_from=divergence`). Since the confirmation's response can be reused when resuming, it was over-counting by one step per branch. Fixing it moved v02's live step ratio from 1.113 to 1.000. **The verdict stays NEGATIVE** (the criterion is 0.6).
- The verdict is NEGATIVE. The parts bearing on the method's correctness held (outcome agreement between branch re-execution and normal execution = 1.0; self-branch billed steps = 0), but the savings claim did not. The cause is that retracing a prefix needs one "decision confirmation" call per step, and once the version changes that is always billed. v02 changes format at the second step (calendar_create), so it diverges early and ends up costing more than a normal run — two confirmations plus the re-execution after divergence. The token ratio is 1.024, lower than the step ratio, because the shared prefix does benefit from the cache.
