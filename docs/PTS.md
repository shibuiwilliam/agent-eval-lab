# 3章 PTS の作り直しと検証

*English: [PTS.en.md](PTS.en.md)*

実施日: 2026-09-20 / 対象: 原典 3.2〜3.8（Predictive Test Selection）

E3-3 は「不確実性 `H(p̂)` による選択はランダムに勝てない」という否定的結果を出した。
**PTS は産業界で実効性が確認されている仕組み**なので、否定的結果が手法の限界なのか
こちらの作り方の問題なのかを切り分ける必要があった。本稿はその作り直しの記録である。

## 0. 結論

| | 前 | 後 |
|---|---|---|
| PASS | 15 | 15 |
| NEGATIVE | 5 | **6** |
| FAIL | 7 | **8** |
| 実験数 | 27 | **29** |

**原典 3.4 の主張は 2 つに分解できる。分解すると、成り立つ部分と成り立たない部分がはっきりした。**

| 主張 | 実験 | 結果 |
|---|---|---|
| (a) 特徴量から `p̂_t` を推定すれば選択に使える | **E3-8**（新設） | **予測は成立**（AUC 0.826）。ただし選択の再現率は基準未達 |
| (b) 不確実性 `H(p̂)` の高いテストを選ぶとよい | E3-3 | **成立しない**（ランダムに劣る） |
| (c) ε-探索は選択器の校正を保つ（3.8） | **E3-9**（新設） | **肯定も否定もできない**（効果量が測定誤差以下） |

E3-3 の仮説と基準は**書き換えていない**（ADR-025）。失敗した仮説を書き換えるのは
「基準に合うまで弄る」ことなので、分解した別の仮説を新しい実験として立てた。

## 1. 根本原因は「学習データが無かった」こと

原典 3.8 は**コールドスタートの手順を明記している**。

> 学習データ（変更 → 合否反転）がない初期は、プロンプト摂動やモデル入替といった
> 合成変更を人為的に加えて反転データを作る。（原典 3.8）

**プロジェクトはこれを実施していなかった。** 変更イベントは植込み版 8 件しかなく、実測すると:

| | 改訂前 | 改訂後 |
|---|---|---|
| 変更イベント | 8 | **37**（合成変更） |
| うち回帰を生むもの | 3 | **18** |
| 学習データの行数 | 368 | **1,702** |
| 陽性（回帰）の数 | — | **108**（4.2%） |
| 慢性失敗率 | 20.7% | 同左（ベースラインは共通） |

8 件中 5 件が回帰を 1 件も生まない状態で「教師あり故障予測」を検証するのは不可能だった。
`pts/synthetic.py` で v01_baseline を摂動した 37 件を機械的に作り、
46 タスク × 5 反復で 8,740 run の専用コーパスを `data/pts_corpus/` に作った（ADR-024）。

合成変更の内訳: プロンプト section の増減 13 / 設定 7 / ツール schema 1 / モデル入替 1 /
**ツール障害 12** / 2 要因同時 3。

## 2. 作り直しの過程で見つかった欠陥 4 件

### D1【重大】障害注入がツールを実行してからエラーに差し替えていた → ADR-026

`_execute_tool` は**環境に対してツールを実行してから**応答を `FaultInjector` に通していた。
`fault="error"` は応答を差し替えるだけなので、**書き込みは成立したまま「失敗した」ことになる**。

`calendar_create` に障害を入れた版で、エージェントはエラーを受け取って「作成できなかった」と
振る舞うのに、受入基準の `event_exists(...)` は DB を見て **True** を返していた。

| 障害を入れたツール | 種別 | 回帰タスク数（修正前 → 修正後） |
|---|---|---|
| calendar_search / mail_search / file_read / external_lookup | 読取 | 11 / 4 / 5 / 5 → 変化なし |
| calendar_create | 書込 | **0 → 10** |
| mail_send | 書込 | **0 → 11** |
| file_write | 書込 | **0 → 9** |
| calendar_delete / file_delete | 書込 | 0 → 1 / 2 |

**書き込み系 6 件がきれいに 0 だった**ので気づいた。実験の合否だけを見ていたら見つからない。
`timeout` / `error` は実行せずにエラーを返すよう直し、`partial` / `schema_change`
（成功した応答を加工する障害）は従来どおり実行後に適用する形にした。

### D2【重大】設定変更がモデルから見て区別できなかった

`max_steps=3` と `max_steps=6` の特徴ベクトルが**完全に一致していた**。
変更側の特徴量が `change_kind_config` と `n_components` しか無かったためで、
設定変更は原理的に学習できない状態だった。
「変更 × テスト」の交差特徴（`max_steps_headroom = max_steps − そのテストの平均ステップ数` など）を足した。

### D3【重大】モデルを決め打ちしていた

最初の実装は `best = results["gbdt"]` とモデルを固定していた。
GBDT は陽性 108 件に対して過学習し AUC 0.638、ロジスティックは 0.759 だった。
ここで「良いほうを選ぶ」のは結果を見てからの選択になる。
**訓練フォールドの中だけで候補を比べる入れ子交差検証**に直した
（外側の hold-out は一切見ない）。内側 CV は全フォールドでロジスティックを選んだ。

### D4【重大】評価と学習の単位が食い違っていた → ADR-027

大域 AUC で評価していたが、**テスト選択は変更ごとに行われる**。
ある変更で上位 k 件を選ぶとき効くのは「その変更の中での順位」だけである。

構造的な帰結（判定を見なくても成り立つ）: **ある変更の中で値が一定の特徴量は、
その変更内の順位付けに一切寄与できない**（スコアに定数を足しても順序は変わらない）。
`change_kind_*`・`max_steps`・`n_components` はまさにこれに当たる。

| モデル | 大域 AUC | 変更内 AUC |
|---|---|---|
| カバレッジ重なりのみ | 0.793 | **0.858** |
| ロジスティック（改訂前） | 0.759 | 0.730 |
| GBDT | 0.638 | 0.624 |

大域 AUC と変更内 AUC が**逆方向に動いていた**。連続値の交差特徴について
「変更の中での百分位順位」を足したところ、大域 AUC は 0.747 → **0.826** に上がった。

## 3. E3-8 の結果: 予測は成立、選択は届かない

### 学習は成立している

| 指標 | 値 | 基準 |
|---|---|---|
| ROC AUC（族単位 leave-one-group-out） | **0.826** | ≥ 0.75 ○ |
| ROC AUC（変更単位 hold-out、診断） | **0.842** | — |
| 変更内 AUC | 0.761 | — |
| カバレッジ単独の AUC | 0.793 | — |
| 履歴故障率のみ（変更を見ない対照） | **0.553** | — |

変更を見ない対照がほぼ偶然（0.553）なので、**予測には変更の情報が要る**ことが確認できた。
変更 1 件だけを hold-out する現実的なプロトコルでは学習（0.842）がカバレッジ単独（0.793）を上回る。

特徴量の寄与（上位）:

| 特徴量 | 寄与 |
|---|---|
| `hist_regress_rate_same_kind`（同じ種類の変更での過去の回帰率） | 0.096 |
| `plan_first` | 0.062 |
| `coverage_overlap_rank_in_change`（変更内でのカバレッジ順位） | 0.059 |
| `max_steps` / `max_steps_headroom` | 0.057 |
| `summarize_headroom_rank_in_change` | 0.051 |

原典 3.4 の表にある「反転回数」「カバレッジ重なり」が実際に上位に来ている。

### 選択の再現率は届かなかった

予算 30% での回帰の再現率（予算内の上限は 0.944）:

| 方策 | 再現率 | 逃走欠陥率 |
|---|---|---|
| 学習モデル | 0.535 | 0.462 |
| カバレッジ重なりのみ | **0.781** | — |
| 等重み順位融合（診断） | 0.739 | **0.270** |
| 不確実性 `H(p̂)` | 0.478 | — |
| 履歴故障率のみ | 0.477 | — |
| ランダム | 0.463 | 0.532 |

**族別に分けると原因がはっきりする。**

| 族 | 変更数 | 学習 | カバレッジ | 融合 | ランダム | 上限 |
|---|---|---|---|---|---|---|
| combo | 2 | 0.667 | 0.500 | **1.000** | 0.683 | 1.000 |
| config | 2 | 0.107 | 0.143 | **0.607** | 0.303 | 0.822 |
| **fault** | **10** | **0.448** | **0.926** | 0.729 | 0.445 | 0.945 |
| prompt | 3 | 0.867 | 0.900 | 0.767 | 0.534 | 0.967 |
| tool | 1 | **1.000** | 0.800 | 0.500 | 0.312 | 1.000 |

**学習モデルは `fault` 族以外ではカバレッジと同等か上回るが、`fault` 族で大きく劣る。**
族単位 hold-out では「ツール障害」という種類の変更を一度も見ずに予測することになり、
カバレッジをどれだけ信用してよいかを**カバレッジが効かない種類の変更から学んでしまう**。
評価可能な 18 件のうち 10 件が fault なので、平均がこれに引きずられる。

逆に `config` 族はカバレッジが原理的に効かない（設定変更は `C(Δ)` が空になる）ため、
カバレッジ単独は 0.143 しか取れない。学習モデルも 0.107 と低いが、
**融合すると 0.607 まで上がる**。

### 基準の到達可能性を点検した

`recall_ratio_vs_random ≥ 2.0` は絶対再現率 **0.926** を要求するが、予算内の上限は **0.944** しかない。
**この基準はほぼオラクル性能を要求していた。** 基準は実装前に固定したので変えないが、
基準の設計が厳しすぎたことを記録する。予算 30% でランダムが既に回帰の 46% を拾うのは、
46 タスク中 19 件を選べるためである。

### 実務的な含意

学習スコアとカバレッジを**変更内の百分位順位で等重み融合**すると（重みは調整していない）、
逃走欠陥率が 0.462 → **0.270**（ランダム比 0.507）に下がる。

> **依存グラフ（原典 3.2）を学習モデルに溶かし込まず、別系統として残して融合する。**
> 未知の種類の変更が来たときの保険になる。

これは族別の結果を見た後に足した方策なので判定には使っていないが、
実務でそのまま使える形の推奨である。

## 4. E3-9 の結果: 肯定も否定もできない

原典 3.8 は ε-探索に「選択器の校正を保つ」という役割を与えている。
部分観測（選んだテストの結果しか見えない）で 37 件の変更を逐次処理し、
探索比 ε ∈ {0, 0.05, 0.2} を比べた。

**最初の実装は並び順を 1 通りしか試しておらず、そのときは校正の改善が +0.006 と出ていた。**
並び順を 5 通りに増やして**対応のある比較**（同じ並び順で ε=0 と ε=0.05 を比べる）にすると:

| 指標 | 値 | 基準 |
|---|---|---|
| `calibration_gain`（後半 Brier の改善） | **−0.0023**（対応差の SD 0.0088） | > 0 × |
| `escape_gain`（後半逃走欠陥率の改善） | +0.0096（SD 0.070） | ≥ 0 ○ |
| `exploration_cost` | 0.0487 | ≤ 0.10 ○ |
| `exploration_gain`（探索が勝ったラウンドの利得） | 0.0576 | — |

**効果は消えた。1 通りの結果は並び順のばらつきを拾っていただけだった。**

検出力を計算すると、この効果量を 80% の検出力で拾うには並び順が **113 本**要る
（逃走欠陥率のほうは **407 本**）。5 本では足りない。
つまりこの実験は「探索に効果が無い」ことを示したのではなく、
**あるとしても 5 本の並び順では見えない大きさである**ことを示した。

ただし **探索の費用は基準内**で、差し引きではむしろ探索のほうがわずかに得をしている
（費用 0.049 に対し利得 0.058、後半の再現率は 0.736 → 0.757）。
「探索は当該ラウンドの性能を大きく犠牲にする」という懸念は否定できた。

副次的な観測として、**全件観測（完全情報）の後半 Brier は 0.088 で、部分観測の ε=0（0.068）より悪い**。
データが多いほど校正が良くなるとは限らない。全件観測は簡単な陰性を大量に学習に入れるので、
陽性の少ないこの設定ではかえって確率が縮む方向に働く。
上限として置いた対照が上限になっていなかった、という観測である。

## 5. 3章全体の読み方

| 節 | 手法 | 実験 | 判定 | 要点 |
|---|---|---|---|---|
| 3.2 | 軌跡カバレッジ依存グラフ | E3-1 | PASS | 反転 11 件をすべて候補に含み、候補は全体の 34.8% |
| 3.3 | 意味的影響推定 | E3-2 | PASS | 条件付き（タグ列挙は決定的抽出） |
| 3.4 | 不確実性駆動の選択 | E3-3 | NEGATIVE | `H(p̂)` はランダムに勝てない |
| 3.4 | **学習済み故障予測** | **E3-8** | **FAIL** | **予測は成立（AUC 0.826）、選択の再現率が未達** |
| 3.5 | テストピラミッドの段判定 | E3-4 | PASS | 条件付き |
| 3.6 | 接頭辞キャッシュと分岐再実行 | E3-5 | NEGATIVE | 節約は成立しない |
| 3.7 | SPRT 早期打切り | E3-6 | PASS | 固定 n の 0.544 倍 |
| 3.8 | 逃走欠陥率・ε・不可侵集合 | E3-7 | NEGATIVE | 骨格は成立、選択性能が未達 |
| 3.8 | **探索と校正** | **E3-9** | **NEGATIVE** | **効果量が測定誤差以下（肯定も否定もできない）** |

**3 章全体の結論**: この環境で確実に効いているのは **3.2（依存グラフ）** である。
3.4 の不確実性は選択の規準としては効かず（E3-3）、
教師あり学習は予測としては成立するが依存グラフを超えられない（E3-8）。
規模（変更 37 件・陽性 108 件）が産業用 PTS（数十万コミット）と桁違いであることが効いている。

## 6. 次にやるなら

1. **合成変更を数百件に増やす**。E3-8 の族単位 hold-out が厳しすぎるのは、
   各族の変更が 1〜13 件しか無いため。族内に多数の変更があれば
   「見たことのない種類」という設定が緩み、産業用 PTS の条件に近づく
2. **E3-9 の並び順を 100 本にする**。検出力の計算から必要本数は 113 本と出ている
3. **融合方策を正式な仮説として立て直す**（E3-8 の診断を、基準を先に固定した新実験にする）
4. **タスクのツール列を多様にする**。E3-3 の冗長性ペナルティの問題と同根で、
   sim の軌跡が 13 種類のツール名列しか持たないことが選択の評価全体に効いている
5. **live で確かめる**。合成変更は sim のシミュレータの挙動フラグを経由しているので、
   実モデルで同じ回帰パターンが出るとは限らない（E0-1 の L6 と同じ懸念）
