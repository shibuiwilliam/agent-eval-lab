## 0. 要旨

### 0.1 このレポートの位置づけ

本プロジェクトは、エージェント評価の手法を「実装して動いた」ではなく、**植え込んだ欠陥に反応し、対照には反応しない**ことで検証してきた。
対象は 2 つある。

| 部 | 対象 | 検証の場 | 実験 |
|---|---|---|---|
| 第 I 部 | AIエージェント一般のテスト・評価（原典 3・4・8 章。5・6 章は関連する範囲で） | 合成オフィス環境（SQLite、14 ツール、46 タスク、13 版） | 30（E3-x・E4-x・E8-x・E0-x） |
| 第 II 部 | エージェンティックコーディングでソフトウェアを開発するための**ハーネス**のテスト・評価 | 自作 Python リポジトリ 6 個、バグ修正などのタスク 48 件、Docker のサンドボックス | 6（EC-S1・O2・B2P・B2・R1・R2） |

各部の各テーマを「課題 → 手法 → 検証で分かったこと → 工夫」の順に書く。手法の中身は原典と NEW_IDEA が正であり、
本レポートの役割は、**その手法を実際に検証したら何が成り立ち、何が成り立たず、どう進めると誤らずに済むか**を整理することにある。

### 0.2 主要な数値

| 項目 | 値 |
|---|---|
| 実験 | **36**（オフィス 30 ＋ コーディング 6） |
| 判定 | PASS **21** / NEGATIVE **6** / FAIL **9** / PENDING 0 |
| 合格基準 | オフィス 106 個中 87 達成（82.1%）、コーディング 27 個中 26 達成・1 個 N/A（検出力不足で判定から除外） |
| live API | オフィス 1,617 呼び出し / 3.80 USD、コーディング 7,344 呼び出し / 28.07 USD（台帳の累積 31.87 USD） |
| 軌跡 | オフィス sim 5,760 run ＋ PTS 用 15,180 run、コーディング live 544 run |

### 0.3 結論

1. **評価手法の多くは主張どおりに働く。ただし、評価器のほうが先に壊れている。**
   オフィスでは欠陥 21 件のうち 16 件、コーディングでは 9 件すべてが評価器・手続きの側にあった。
   どれも「実験が通っているか」を見ているだけでは見つからなかった。
2. **出力だけの評価は、過程の劣化と静かな誤りを原理的に見逃す。**
   オフィスでは合格率がまったく同じ 3 版が、検証行動率 1.00 / 0.00 / 1.00、重複呼出率 0.004 / 0.005 / 0.191 に分かれた。
   コーディングでは可視テストの合格率 0.986 と 0.938 でほぼ並ぶ 2 版が、静かな誤りの率では 0.076 と 0.236 に分かれた。
3. **否定的結果は、原典の主張の穴を指している。** 不確実性駆動の選択は KPI と目的関数が食い違う、
   分岐再実行は版を変えると節約しない、成果物だけの弁別力は過程の劣化を拾えない、決定的な代替ジャッジは一貫して甘い。
4. **ハーネス評価の手法として「確立した」とは言えない。** 部品ごとの寄与の測定は未着手で、根拠は 1 モデル・小さな自作リポジトリに限られる。
   そのうえで、使用量記録からのコスト帰属、変更の費用効果の事前予測、可視／隠しテストの二層化と S / W / F 分解、
   実現可能な pass@k、効果モニタと評価基盤の検証は、植込みと対照で働くことを確かめた。
5. **評価の進め方の工夫が、手法と同じくらい結果を左右した。** 基準を実装前に固定する、ベースラインだけのパイロットで
   到達上限と検出力を出す、植込みの操作確認、失敗したときの読み方の事前固定、N/A と合格の区別。
   これらが無ければ、少なくとも 1 件の植込みの不発を「手法が働いた／働かなかった」と取り違えていた。

## 1. 共通の前提

### 1.1 なぜエージェントの評価は難しいか

原典 1 章は、エージェント評価が難しい理由を「次の性質が**同時に**成り立つこと」に置く。
確率的で多段なので 1 回の合否は信用できず反復が要るが、1 回が高価なので反復できない。
正解が複数あるので模範解答の比較では足りないが、軌跡が長すぎて人が読めない。
環境に依存するので模擬が要るが、模擬は現実から離れていく。

コーディングエージェントでは、さらに次の性質が加わる（NEW_IDEA 1 章）。

| 性質 | 素朴な評価が誤る点 |
|---|---|
| 環境に本物の検証器（テスト）があるが、エージェントはそれを読み、書き換えられる | 「テストが通った」を成功と数えると、テストの改変や特殊化も成功と数える |
| テスト実行は任意コード実行と等価である | コマンドの許可リストで権限を評価すると、許可済みのコマンドを経由した効果を見逃す |
| コストの大半はトークンではなく、人のレビューと漏れた欠陥の後始末である | トークン削減を最適化すると、ROI がかえって下がりうる |
| 振る舞いの多くがモデルではなくハーネスで決まる | エージェント・ハーネス・モデルのどれが良くなったのかが分離できない |
| 時間と費用が、ツール出力が会話に残り続けることに支配される | 総トークンだけ見ても、どこを直せば安くなるかが分からない |

### 1.2 原理

原典は 3 つの原理を置き、NEW_IDEA はそれを 4 つに拡張した。本レポートの全テーマはこの組合せで説明できる。

| 原理 | 内容 | 主に効くテーマ |
|---|---|---|
| 原典 1　情報量／コストの最適化 | 人の注意・ライブ実行・金銭を、結果が最も不確実な所に集中させる | PTS、SPRT、人の配分 |
| 原典 2　主張ではなく証拠 | 自己申告ではなく、ツールログと環境の最終状態を根拠にする | 過程の評価、ジャッジの設計 |
| 原典 3　評価系そのものが劣化する製品 | テスト・模擬・ジャッジ・選択器にも指標と寿命を持たせる | 陳腐化対策、評価基盤の検査 |
| NEW_IDEA A　効果で評価する | 主張でもコマンドでもなく、差分・起動・読み書き・送信という**効果**で評価する（原典 2 を一段進めたもの） | 静かな誤り、効果モニタ |
| NEW_IDEA B　最初の分岐点までは再生で厳密 | 2 条件の入力が最初に食い違うステップ j までは、記録の再生が正しい標本になる | 分岐再実行、ハーネスの反実仮想 |
| NEW_IDEA C　ROI は点ではなく決定として出す | 測れない人件費を範囲 Θ で掃引し、決定が変わらない割合 Rob を出す | ハーネスの費用対効果 |
| NEW_IDEA D　計測器を先に検証し、基準は上限と検出力から置く | 真値の分かる代役で計測器を検査し、ベースラインだけのパイロットから基準を決める | 全テーマ |

### 1.3 検証の背骨

評価手法 M が「検証できた」と言えるのは、次の 2 つを同時に満たすときだけである。

```
植込み条件（欠陥を入れた版・タスク・注入） ──→ M ──→ 反応する
対照条件（ベースライン、無関係な変更）     ──→ M ──→ 反応しない
```

各実験は、実装より先に 5 項目（仮説、植込み条件、対照、数値の合格基準、来歴）を結果ページに書いた。
基準は後から緩めず、緩めるなら ADR を書く。届かなければ **FAIL**（こちらの実装・設計の不備）と
**NEGATIVE**（実装は正しいが主張が成り立たない）に分けて残す。数値には来歴（`live` = 実 API、`replay` = 記録の再生、
`simulated` = 決定的シミュレータやスクリプト化エージェント、`unit` = 単体テスト）を付け、混ぜない。

# 第 I 部　AIエージェントのテストと評価

## 2. 過程を評価する

### 2.1 課題

結果と過程は独立に良し悪しを持つ（原典 4.1）。結果だけを見ると「過程は悪いが結果は正しい」
（偶然の正解、報酬ハック、検証の省略、過剰なコスト）を成功と数え、「過程は良いが結果は誤り」
（ツール障害、環境の揺らぎ）をエージェントの失敗と数える。コスト・安全性・再現性は過程にしか現れない。

本プロジェクトの実測が、この問題をそのまま示した。

| 版 | 合格率 | 検証行動率 | 重複呼出率 |
|---|---|---|---|
| v01（ベースライン） | 0.7935 | 1.00 | 0.004 |
| v03（検証を省く植込み） | 0.7935 | **0.00** | 0.005 |
| v04（ループを起こす植込み） | 0.7935 | 1.00 | **0.191** |

3 版の合格率は小数 4 桁まで同じである。合格率だけの評価では、この 2 つの劣化は存在しない。

### 2.2 手法（原典 4 章）

| 手法 | 要点 |
|---|---|
| 軌跡メトリクス | 迂回率 $L_{\text{actual}}/L_{\min}$、重複呼出率、後戻り、検証行動率、停止適切性、質問適切性など。単独で使わず、対になる品質指標と組で報告する |
| アブレーションによる無駄判定 | ある呼び出しの結果を消して以降を再実行し、最終結果が変わらなければ無駄と判定する。安価な代理指標を全件に、アブレーションをサンプルに当てて校正する |
| 軌跡リンター | 「削除の前にバックアップ」「完了宣言の前にテスト実行」などを時相論理風の制約として書き、構造化ログに決定的に当てる。LLM を使わず、正解経路が複数でも壊れない |
| 半順序マイルストーン | 黄金軌跡の代わりに、到達すべき中間状態・順序制約・禁止行動だけを指定し、部分点を与える |
| ステップ単位判定 | 各状態での行動の妥当性をジャッジまたは参照方策との一致で採点する。平均に加えて最小値を見る |
| 計画の外在化と乖離率 | 計画を DAG として出力させ、実行前に検査し、実行後に計画と行動の編集距離を取る。乖離箇所だけをジャッジに問う |
| 軌跡内 Needle-in-a-Haystack | 早い段階のツール出力に鍵情報を埋め、ノイズを挟んだあとで使えるかを測る。コンテキスト管理戦略の比較に使う |
| pass@k と pass^k | 前者は能力の上限、後者は信頼性。毎回同じ仕事を任せるなら後者が要る |
| コスト予算と Goodhart ペア | p95 のトークン・ステップ予算を強制し、効率指標は必ず品質指標（検証行動率など）と組にする |

### 2.3 検証で分かったこと

| 手法 | 実験 | 判定 | 主要な数値 [simulated] |
|---|---|---|---|
| 軌跡メトリクス | E4-1 | **PASS** | 重複呼出率が v04 で 44 倍、検証行動率が v03 で 0 倍。無関係な植込み v02 は揺らぎの帯の内側 |
| アブレーション無駄判定 | E4-2 | FAIL | 無駄率の差 0.024（基準 0.15）。ベースラインでも U が 0.889 に張り付く天井効果 |
| 軌跡リンター | E4-3 | **PASS** | 違反の検出率 1.0、ベースラインの誤検出 0.0 |
| 半順序マイルストーン | E4-4 | FAIL | 合成軌跡の順序判定は成立。4 版での Spearman ρ = −0.272（全 12 版なら 0.630、p = 0.028） |
| ステップ単位判定 | E4-5 | **PASS** | 変異ステップの低下率 0.967（ルーブリック）/ 1.000（参照方策） |
| 計画の外在化と乖離率 | E4-6 | FAIL | δ が 0.219 → 0.416 と約 2 倍だが、差 0.197（基準 0.2） |
| 軌跡内 NIAH | E4-7 | FAIL | R(0) = 1.0、低下 0.667 は成立。run が 2〜3 ステップで要約が発火せず、戦略の比較ができない |
| pass@k / pass^k | E4-8 | **PASS** | 境界タスクで差 0.749、自明タスクで 0.000 |
| Goodhart ペア | E4-9 | **PASS** | 効率化の植込み v07 はステップ 0.796 倍・検証行動率 0 倍・合格率は据え置き |

**成り立ったこと**: 過程の指標は、合格率が動かない劣化に選択的に反応する（E4-1・E4-3・E4-9）。
効率指標を単独で最適化すると検証が消えるという原典 4.11 の警告は、そのとおりに再現した。

**成り立たなかったこと**: FAIL の 4 件はいずれも実験設計側（天井効果、標本の版数、境界ぎりぎりの基準、環境の run が短すぎる）である。
手法の主張そのものを否定した結果は無い。

### 2.4 工夫と教訓

- **決定的な手法から入れる。** リンター（E4-3）、pass@k（E4-8）は LLM に依存せず、sim と live の別が結果に影響しない。
  原典 10 章の導入順（基盤 → リンター・コスト予算 → …）は、検証の通りやすさの順とも一致した
- **過程の指標は作法の差に敏感である。** live の被験エージェントは完了宣言のツール（`finish`）を呼ばずに終わることがあり、
  それを起点にしたリンター規則が live では発火していなかった（実 API で動かして初めて分かった欠陥の 1 つ）。停止適切性を原典 4.2 の定義（未達の完了宣言・達成後の継続）で
  測り直すと live 0.496 / sim 0.500 で一致し、食い違っていたのは「`finish` を呼ぶか」という作法（live 0.683 / sim 1.000）だった。
  **過程の指標は、どの行動を起点にしているかを live の軌跡で確かめてから使う**
- **環境が手法の前提を満たすかを先に確かめる。** NIAH（E4-7）は要約が発火する長さの run を、アブレーション（E4-2）は
  無駄な呼び出しが一定数ある run を前提にする。前提を満たさない環境では、手法は「働かない」のではなく「試せない」

## 3. Predictive Test Selection

### 3.1 課題

エージェントのテストは 1 回が高く、全件を毎回は走らせられない。しかもエージェントの「変更」は多層で
（コード、プロンプト、モデル版、ツール仕様、知識ベース、設定、外部環境）、**何も変えていないのに壊れる**（原典 3.1）。
コードの PTS の「変更ファイルとその近くのテスト」だけでは、どのテストを選べばよいか決まらない。

### 3.2 手法（原典 3 章）

| 手法 | 要点 |
|---|---|
| 軌跡カバレッジ依存グラフ | 過去の軌跡から各テストの使用要素 $U(t)$ を取り、変更が触れる要素 $C(\Delta)$ と交わるテストを候補にする |
| 意味的影響推定 | プロンプトの差分を LLM に読ませて変わりうる行動をタグ列挙し、テストと照合する |
| 不確実性駆動の選択 | 予測合格率 $\hat p_t$ のエントロピー $H(\hat p_t)$ をコストで割った順に、類似テストを間引きながら詰める |
| テストピラミッド | L0（決定的部品）〜 L5（本番カナリア）のどの段まで登るかも選ぶ |
| 接頭辞キャッシュと分岐再実行 | 各ステップの状態を保存し、新版が旧軌跡から分岐した地点以降だけを live で走らせる |
| SPRT による早期打切り | 合否の反復を逐次確率比検定で決着した時点で止める |
| 選択器の運用 | 合成変更によるコールドスタート、逃走欠陥率 $\mathrm{Escape}(S)$ の追跡、ε-探索、不可侵集合、履歴の再学習 |

### 3.3 検証で分かったこと

| 手法 | 実験 | 判定 | 主要な数値 [simulated] |
|---|---|---|---|
| 軌跡カバレッジ依存グラフ | E3-1 | **PASS** | 反転したテストをすべて候補に含み、候補は全体の 34.8% |
| 意味的影響推定 | E3-2 | **PASS** | 再現率 1.0、対照の選択率 0.0 |
| 不確実性駆動の選択 | E3-3 | NEGATIVE | 校正誤差 0.080 は満たすが、逃走欠陥率はランダムの 1.06 倍 |
| テストピラミッドの段判定 | E3-4 | **PASS** | 段の一致率 1.0 |
| 接頭辞キャッシュと分岐再実行 | E3-5 | NEGATIVE | 結果の一致率 1.0 だが、live ステップ比 1.000（基準 0.6） |
| SPRT | E3-6 | **PASS** | α 0.046 / β 0.052、試行数は固定 n の 0.544 倍 |
| 逃走欠陥率・ε・不可侵集合 | E3-7 | NEGATIVE | 不可侵集合 1.0、予算 100% で逃走 0 だが、予算 40% で 0.479（基準 0.1） |
| 学習済み故障予測 | E3-8 | FAIL | AUC 0.814、予算 30% の再現率 0.819、逃走欠陥率はランダムの 0.319 倍。ランダム比の再現率 1.76（基準 2.0、到達上限との差 0.001） |
| 探索と校正 | E3-9 | NEGATIVE | 校正の改善 −0.0023。効果量が並び順のばらつきに埋もれる（必要な並び順は約 113 本） |
| 変更履歴に沿った逐次評価 | E3-10 | FAIL | 逐次 AUC 0.761、学習の積み上がりは成立。履歴特徴の寄与 −0.075 |

### 3.4 工夫と教訓

- **目的関数と KPI を揃える。** 原典 3.4 は情報利得（不確実性）を最大化し、3.8 は逃走欠陥率で選択器を評価する。
  $H(\hat p)$ は $\hat p = 0.5$ で最大なので、ほぼ確実に落ちるテスト（$\hat p \to 0$）を優先しない。
  E3-3 の NEGATIVE は、原典の 2 つの節が別の最適化問題を解いていることを示した。
  不確実性の役割は選択ではなく探索と校正（E3-9）だと読み直すのが妥当だが、その効果はこの規模では測れなかった
- **分岐再実行の節約は「何を変えたか」で決まる。** 版（システムプロンプト）を変えると最初のリクエストから入力が変わり、
  分岐点 j = 0 なので節約は原理的に出ない（E3-5）。NEW_IDEA の原理 B はこれを一般化し、
  **版を固定して環境やハーネスの側だけを変える反実仮想なら、節約は j / L になる**と整理した（第 II 部 13 章）
- **選択器には変更履歴の台帳が要る。** 当初の変更 8 件では、学習が依存グラフの 1 行のヒューリスティクスに負けた。
  原典 3.8 のとおり合成変更でコールドスタートし（65 件、陽性 4.1%）、変更に順序を与えて「前回その要素が変わってからの間隔（ラグ）」と
  変更量を特徴量にすると、予算 30% の再現率が 0.535 → 0.819、逃走欠陥率がランダムの 0.868 倍 → 0.319 倍になった。
  ラグは変更に順序が無いと定義できないので、順序の無い集合として変更を扱っていた実装では「書き忘れた」のではなく「書けなかった」
- **最も効く特徴量は少数である。** 履歴の特徴群を全部入れると陽性 122 件に対して過学習し、AUC が 0.747 まで落ちた。
  ラグだけを足したときが最良（0.878）だった
- **「ランダムの N 倍」という形の基準は、対照が強いと到達不能になる。** E3-8 の比の基準は到達上限との差が 0.001 しかなかった。
  絶対値で書いていれば PASS だった

## 4. LLM as Judge と Human-in-the-loop の組み合わせ

### 4.1 課題

LLM ジャッジは規模と一貫性に優れるが、正解を知らず、エージェントの主張に騙され、長い軌跡の中盤を落とす。
人は正解・趣味・新奇な故障の発見に優れるが、高価で遅く、疲れる（原典 5.1）。オンラインでは正解が無く、遅延制約があり、
副作用が本物である（原典 6 章）。さらに、人の承認ゲートは健全性を測らないと形骸化し、ジャッジのスコアで
エージェントを調整するとジャッジが攻略される。

### 4.2 手法（原典 5・6 章）

| 手法 | 要点 |
|---|---|
| 定義は人、適用は LLM | ルーブリック・仕様・リンター規則・ゴールデンセットは人、一次判定・クラスタリング・要約は LLM。不一致の裁定と重大度は人 |
| 主張と証拠の分離 | 最終要約や「確認しました」を隠し、生のツールログと環境状態だけをジャッジに見せる。判定根拠に証拠の参照を必須にする |
| ツール付きジャッジ | 読むだけでなく、最終状態を検査し、テストを走らせ、差分を取る |
| ジャッジのミューテーションテスト | 良い軌跡に既知の欠陥（引数改変、検証省略、破壊的操作、偽の完了報告、順序の入替、ループ、スコープ逸脱）を注入し、検出率 MS と誤警報率を測る。ジャッジの回帰テストにする |
| 人の配分 | ジャッジ間の不一致・低信頼は人の裁定へ、それ以外は層化抽出で監査してジャッジの誤り率を推定する。失敗はクラスタ代表だけを人が見る |
| ルーブリック蒸留 | 人のコメントをルーブリック項目やリンター規則に変換し、人の 1 時間を複利で効かせる |
| メタ評価の常設 | 対人一致 κ、再判定一致率、ミューテーションスコア、誤警報率、コストをエージェントの指標と同じ場所に置く |
| オンラインの二つの時間軸 | 同期側は止めるための軽い検査（ルール・リンター）、非同期側は測るための重いジャッジ |
| 承認ゲートの健全性 | 承認率・介入の精度・介入の再現率。承認率がほぼ 100% ならゲートは形骸化している |
| 統計的工程管理とホールドアウトジャッジ | ジャッジスコアを CUSUM で監視する。学習信号用と監視用のジャッジを分け、後者を開発ループから隔離する |

### 4.3 検証で分かったこと

原典 5・6 章そのものは本プロジェクトの検証範囲（3・4・8 章）の外にある。ただし、ジャッジと人の判定に関わる部分は
次の実験で確かめた。

| 対象 | 実験 | 判定 | 分かったこと |
|---|---|---|---|
| ジャッジのミューテーションテスト | E4-5 | **PASS** | 変異（誤ツール・誤引数・破壊的操作）を入れたステップの評価が下がる率 0.967 / 1.000 [simulated] |
| live ジャッジと決定的代替判定器 | E0-2 | NEGATIVE | live の Sonnet 5 は変異の低下率 0.989、再判定の一致 1.000（完全一致 0.967）で安定 [live]。代替判定器との一致は ±1 以内で 0.683（基準 0.7） |
| 乖離箇所だけをジャッジに問う | E4-6 | （FAIL の一部） | 乖離の正当性判定の率 0.978。判定対象を軌跡全体から数箇所に絞れる |
| 本番→テストの承認 | E8-7 | （FAIL の一部） | 起草した受入基準の承認率 1.0。ただし自動承認（承認条件を機械的に定義）で、人の承認ではない |

E0-2 の中身は示唆に富む。**決定的な代替判定器は一貫して甘い**。元のステップで live 3.7 に対して代替 4.87、
誤ツールの変異では live 1.73 に対して代替 4.0 と 2 点以上開いた。代替判定器は「期待外かつ読み取り系でない」ときだけ減点する規則なので、
読み取り系への誤置換をほとんど罰しない。live のジャッジは「その状況で意味を成さない行動」として強く減点していた。
一方、変異を検出する**向き**は代替判定器でも live でも一致し、E4-5 の結論は live でも支持された。

### 4.4 工夫と教訓

- **代替判定器は向きだけに使い、絶対水準には live のジャッジを使う。** 代替判定器を live に合わせて調整すれば一致率は上がるが、
  それは基準に合うまで実装を弄ることになる。用途を限定して明記するほうが正しい
- **ジャッジの安定性は live でしか測れない。** 代替判定器は決定的なので、E4-5 の再判定一致率は定義上 1.0 になり、
  「判定が安定している」ことを何も検証していなかった。決定的な代役で測った安定性は、安定性の証拠にならない
- **ジャッジの構造化出力はツール呼び出しで強制する。** 本プロジェクトは判定を `submit_verdict` ツールと `tool_choice` 強制で取り、
  本文を正規表現で解析しない。判定の取り出しの失敗を、ジャッジの判断の誤りと混同しないためである
- **ジャッジより決定的な検出器を優先できる所では優先する。** 第 II 部の特殊化検出（可視テストのリテラルが本体の差分に現れるか）や
  効果モニタは、ジャッジを使わずに決定的に判定する。ジャッジは「決定的に書けない判断」に限ると、ミューテーションテストの対象も絞れる
- **人の判断は「定義」と「読み方」に置く。** 第 II 部では、ユーザーが関門（G0〜G2）で設計・予算・live の実行を承認し、
  設計者役のエージェントが結果の解釈を、別の独立したレビュー役が数値の検算を担った。人が担ったのは、
  基準と Θ（測れない人件費の範囲）の確定、植込みが不発だったときの進め方の選択（ADR-046）である。
  人を個々の判定に使わず、判定の**規則**と**失敗時の読み方**に使うと、少ない介入で結論の向きを決められた
- **承認の数字は、承認の仕組みを書いてから読む。** E8-7 の承認率 1.0 は自動承認によるもので、人の承認ゲートの健全性
  （原典 6.3）を測ったものではない。承認率がほぼ 100% のときに形骸化を疑え、という原典の指摘はそのまま当てはまる

## 5. テストの陳腐化対策

### 5.1 課題

「テストは通るが本番で壊れる」は、テストと実利用の乖離から起きる。乖離の源泉は、環境（API や Web の変化）、
タスク分布（新しい用途、ユーザーの共適応）、エージェント（モデルの無断更新、記憶の蓄積）、評価者（ジャッジの更新）、
汚染（テストの学習データへの流入）に分かれ、それぞれ検知と対策が違う（原典 8.1）。

### 5.2 手法（原典 8 章）

| 手法 | 要点 |
|---|---|
| 本番→テスト・パイプライン | 失敗・高コスト・新カテゴリを優先して層化採取し、ジャッジが受入基準を起草、人が検証して登録する |
| 鮮度と分布距離 | テストに作成日を持たせ、スイートと本番の分布距離（JS、MMD）を監視する |
| 飽和と弁別力 | 良い版と悪い版での合格率の差 $d(t)$。$d \to 0$ のテストは難化か引退 |
| 模擬忠実度と TTL | 記録済みのツール応答に寿命を付け、ライブ応答との一致率 F を定期的に測る |
| 二重トラック評価 | 模擬スイートとライブスイートの合否一致 κ で sim-to-real のずれを数値で管理する |
| アサーションの層化 | 状態検査を骨格に、不変条件は厳密一致、表層は意味的判定 |
| ドリフト帰属とモデル指紋 | 1 要素ずつ入れ替えて原因を切り分ける。固定プローブで無告知のモデル更新を検知する |
| 記憶・共適応・汚染 | 老化した状態のフィクスチャ、素朴入力の保存、非公開スイート、カナリア文字列 |
| テストのライフサイクル | Created → Validated → Active → Saturated / Stale → Hardened / Rerecorded / Retired の状態機械。所有者と見直し期限 |

### 5.3 検証で分かったこと

| 手法 | 実験 | 判定 | 主要な数値 |
|---|---|---|---|
| 模擬忠実度と TTL | E8-1 | **PASS** | 外部サービスの版を上げると F が 1.0 → 0.0、不一致キーが完全に一致、TTL 切れの検出率 1.0 [simulated] |
| 鮮度と分布距離 | E8-2 | **PASS** | JS が単調増加、新カテゴリの警報、MMD p = 0.017、対照で p ≥ 0.05 の率 0.95 [simulated] |
| 弁別力と飽和 | E8-3 | NEGATIVE | 自明タスクの飽和判定は成立、境界タスクの弁別力 0.068（基準 0.3） [simulated] |
| 二重トラック κ | E8-4 | **PASS** | ドリフト注入で κ が 1.0 → 0.0 [simulated] |
| ドリフト帰属 | E8-5 | **PASS** | 単一要因 3/3、2 要因の上位 2 一致、対照で警報なし [simulated] |
| モデル指紋 | E8-6 | **PASS** | live の指紋で対照 p = 0.716、モデル入替 p = 0.046 [live] |
| 本番→テスト | E8-7 | FAIL | 承認率 1.0、登録後に JS 0.100 → 0.018。層化の lift 1.89（基準 3.0、上限 2.2 で到達不能） |
| ライフサイクル状態機械 | E8-8 | **PASS** | 全遷移、Retired の終端性、追記型 [unit] |
| 汚染検知 | E8-9 | FAIL | カナリア走査の検出率 1.0・誤検出 0。公開／非公開の合格率差 0.177（基準 0.2） |

8 章は 3 章の中で最も素直に通った（PASS 6 / NEGATIVE 1 / FAIL 2）。LLM に依存しない決定的な手法が多いためである。

### 5.4 工夫と教訓

- **弁別力は「何を見て良し悪しを決めたか」に縛られる。** 成果物の合否だけで定義した $d(t)$ は、
  過程が劣化して結果が変わらない版（第 2 章の v03・v04）を原理的に弁別できない（E8-3）。
  これは原典 4.1「成果と過程は独立の軸」の裏返しで、原典の 4 章と 8 章の間の不整合である。
  テストの寿命を決めるには、過程の指標に対する弁別力 $d_{\text{process}}(t)$ が要る
- **sim-to-real のずれは「どの量について」で答えが違う。** live で検証した結果（E0-1）、合否・ステップ数・検証行動率・停止適切性は
  sim と live で一致したが、`finish` を呼ぶ率（live 0.683 / sim 1.000）、合格率の水準（0.933 / 0.750）、ジャッジのスコア水準は一致しなかった。
  **sim は指標の向きを再現し、作法と絶対水準を再現しない**。第 II 部でコーディング用のシミュレート・エージェントを作らなかったのはこのためである
- **評価系の劣化は、評価器の欠陥として現れる。** 原典 2.3 の「評価系そのものが劣化する製品」は、本プロジェクトでは
  時間による劣化より先に、**作った時点での誤り**として現れた（第 6 章）。ライフサイクル管理は、まず評価器の検査から始めるべきである
- **少額の live が最も効く。** 3 USD 程度の live 検証で、シミュレーションでは構造的に見えない欠陥を 7 件見つけた

## 6. 第 I 部の横断的教訓

### 6.1 欠陥の 76% は評価器の側にあった

オフィス環境で見つけた欠陥 21 件のうち 16 件は評価器側（基準・リンター・指標・統計量）にあった。
被験エージェントではなく、それを測る側である。評価器の定義を 1 つ間違えると結論が逆になる。

| 欠陥 | 修正前 | 修正後 |
|---|---|---|
| 反転の閾値が次元違いの量（ADR-016） | v09 の反転 4 件 | 23 件 |
| 逃走欠陥率の分母が原典と違う（ADR-018） | 校正誤差 0.325 | 0.080 |
| SPRT の固定 n が二標本の式（ADR-023） | 比 0.604（NEGATIVE） | 0.544（PASS） |
| 停止適切性の定義（ADR-019） | sim 1.0 / live 0.66（不一致） | sim 0.500 / live 0.496（一致） |
| 障害注入が書き込みを残す（ADR-026） | 書込系ツールの回帰 0 | 10 / 11 / 9 件 |

見つけ方は、実 API で動かした（7 件）、コードを原典と突き合わせた（9 件）、データの分布を眺めた（3 件。障害を入れた 12 ツールのうち
書込系 6 件だけがきれいに回帰 0 だった）、複数条件で測り直した（2 件）。**どれも「実験が通っているか」を見ているだけでは見つからない。**

### 6.2 基準設計の失敗パターン

自分で置いた基準のうち 3 件が到達不能ないし測定不能だった（E8-7 の lift、E3-8 のランダム比、E3-9 の校正の改善）。
共通する構造は 2 つある。

1. 「ランダム／一様の N 倍」という形の基準は、対照が強い設定では自動的に到達不能になる
2. 効果量と測定誤差の比を先に見積もっていない基準は、測定不能になりうる

**教訓**: 基準を置く前に (1) 予算内の到達上限（オラクル）を計算し、(2) 検出力（最小検出可能効果）を見積もる。
この 2 つは第 II 部で手続きとして固定した（原理 D、ADR-033）。

## 8. 開発の Observability の自動化

### 8.1 課題

AI に開発を任せると、人が軌跡を通読することはできない。そこで記録を自動で取り、自動で検査することになるが、次の問題がある。

- **ツール呼び出しのログは効果の代理にすぎない。** `run_tests` は「テストを走らせる」呼び出しだが、その効果はテストコードが何をするか次第で、
  ファイルの書き込みも秘密の読み出しも起こりうる（原理 A）。呼び出しを記録しても、何が起きたかは分からない
- **評価基盤そのものが黙って壊れる。** オフィス環境の「障害注入が書き込みを残す」（ADR-026）は、合否を見ているだけでは見つからなかった。
  記録を取る仕組みが壊れていれば、記録から導いた結論も壊れる
- **費用がどこから来たかが見えない。** 総トークンは記録されるが、どのツール出力がどれだけの費用を生んだかは分からない
- **何のためのログかが決まっていない。** 「ログは多いほど良い」は保存費用と秘匿の点で誤りで、「最小限でよい」は診断不能を招く

### 8.2 手法

| 手法 | 内容 |
|---|---|
| 効果の観測 | 作業ツリーとハニーポットのファイル差分、Python の監査フック（`open`・`socket.connect`・`subprocess.Popen`）、非 Python コマンドの起動記録、出口（シンク）の走査の 4 層で、起きた効果を記録する。run 固有のカナリアを置き、シンクに現れたら流出の証拠とする（決定的、誤検出なし） |
| 観測スキーマ | `Step` にスパン（LLM・ツール・権限判定・フック・承認待ち・ハーネス）、効果（種類・対象・経由した呼び出し・仲介の有無・実行の有無）、権限判定を既定値付きで足す（ADR-031）。属性名は OpenTelemetry の GenAI 意味規約に合わせ、SDK は入れない |
| 使用量記録からのコスト帰属 | API の `usage`（`input_tokens`・`cache_creation_input_tokens`・`cache_read_input_tokens`）と各ブロックの累積位置を照合し、課金の種類をブロックごとに割り振る。割り振りの和を費用台帳と恒等式で照合する（9 章） |
| 評価基盤の常時検査（EC-O2） | 仲介の完全性（権限判定を伴わない効果 = 0）、秘匿（run 固有の秘密が trace・カセット・台帳・結果ページに現れない）、記録の整合性（孤児スパン・はみ出す子・終了の無いスパン = 0）、拒否の効果残存（拒否・タイムアウト・エラーの操作が効果を残さない）の 4 検査を、コーパスを作るたびに自動で走らせる |
| 判定と表示の自動化 | `agenteval verify` が全実験の基準を照合して判定表を生成する。来歴ラベルの無い数値を拒否し、N/A を合格と分けて表示し、設計者の 1 行の読み方を載せる。結果ページの再生成で、人や設計者が書いた解釈を消さない |
| 診断可能性による評価（EC-O1、未実施） | テレメトリを T0（最終結果）〜 T4（権限判定・ハーネスのイベント・時刻）の累積水準に分け、植え込んだ 12 種の故障を各水準だけで診断できるかと保存量を測り、ログの費用対効果を出す |

### 8.3 検証で分かったこと

| 対象 | 結果 |
|---|---|
| 評価基盤の 4 検査（EC-O2） | 植え込んだハーネスの欠陥 4 種 × 5 run を 20/20 検出、欠陥の無い 67 run（正解パッチ 48 ＋ 双子 19）で誤警報 0 [simulated] → **PASS** |
| コスト帰属と台帳（EC-B2P・B2） | 既存の live 軌跡 240 本、コーディングの 274 本で、割り振りの和が台帳と浮動小数点の誤差（1e−16 の桁）で一致 [live] → **PASS** |
| 反復の独立性の検査 | カセットの鍵に足した塩の不備 0、同一の試行 0 を 336 run で確認（ADR-038） |

限界もはっきりしている。EC-O2 の植込みは「対応する検査が読む記録に痕跡を残す」よう作ったので、検出率 1.0 の一部は構成上である。
検査がツールの自己申告ではなく独立の記録を読んでいることを確かめたのは 1 種（ブローカーを通らない書き込み）だけで、
live コーパスでの誤警報率は基準にしていない（live には「欠陥が無い」という真値が無い）。EC-O1 は第 3 段に残した。

### 8.4 工夫

- **規則を検査に変える。** 「API キーをコード・ログ・カセット・結果ページに残さない」は規則として書いただけでは守られているか分からない。
  run 固有のカナリア秘密を置き、すべての生成物を走査する検査にすると、毎回自動で確かめられる
- **観測と封じ込めを分ける。** 監査フックは決意した攻撃者には回避できるので境界ではない。境界は Docker に置き、
  監査フックは**計測器**として扱い、その再現率を別に測る（11 章）
- **素朴な照合では台帳と合わないことを確かめておく。** 同じ run_id の行を全部足す素朴な照合では誤差 0.712 になった。
  正しい対応づけをしない実装が落ちる基準にしておくと、恒等式の基準が空虚でなくなる
- **解釈は自動生成で消さない。** 結果ページを再生成すると設計者の「気づき・限界」が消える実装だった（欠陥 6）。
  自動ブロックの印より上を保持し、実ページの写しで一字一句の保持をテストする形に直した
- **開発側のエージェントにも観測の規律を課す。** 第 II 部の実装そのものを、役割ごとにモデルを固定したサブエージェント
  （設計・実装・レビュー・実行）で開発した。実行役には「観測した事実だけを返し、解釈しない」を課し、
  終了コードで成否を判断させた。オーケストレーターが `make check` の失敗を見落としてコミットした事故（欠陥 8）は、
  ログの末尾を読んで成否を判断したことが原因で、終了コードで判断する形に改めて止まった

## 9. ハーネスの費用対効果

### 9.1 課題

- **長い run の費用の大半は、過去のツール出力の再送である。** ツール出力は以降のリクエストのたびに入力として送り直されるので、
  詳細なテスト出力 1 回の費用は、それが会話に残るステップ数だけ膨らむ
- **トークン費用は費用の一部にすぎない。** コーディングでは、人のレビューと、漏れた欠陥の後始末が費用の大半を占めうる。
  トークンを削って検証を省けば、ROI はかえって下がる（経済版の Goodhart）
- **人件費は実験室で測れない。** 測れない量を 1 つの値に決め打ちして ROI を出すのは、測定の体裁をとった仮定である（原理 C）

### 9.2 手法

**コンテキスト・コスト帰属（CCA）**: ツール出力 i の生涯コストを、それが送られるリクエスト集合 $M_i$ にわたる課金の和として定義する。

$$
\mathrm{CCA}_i = \tau_i \sum_{m \in M_i} p(m, i)
$$

$\tau_i$ は出力 i のトークン数、$p(m, i)$ はリクエスト m で出力 i に掛かる単価（キャッシュ書き込み・キャッシュ読み出し・通常入力のどれか）である。
課金の種類は、`usage` が示す「キャッシュ区切りまでの接頭辞」と「それより後ろ」の長さを各ブロックの累積位置と照合すると一意に決まる（位置モデル）。
n 回再送される出力の費用比（キャッシュあり／なし）は、Haiku 4.5 の単価で $(1.25 + 0.10(n-1))/n$ になり、n = 10 なら約 0.21 である。
**この比は実行前に計算できる。**

**3 類の正味価値と決定ロバスト性**: 結果を S・W・F に分けると、任せたときの正味価値は

$$
\mathrm{NV} = H - \big[C_a + \pi_S R + \pi_F (R_F + H') + \pi_W (R + rH' + (1-r)D)\big]
$$

になる（H は人が自分でやる費用、$C_a$ はエージェントの費用、R はレビュー、H' はやり直し、D は漏れた欠陥の後始末、r は W がレビューで見つかる率）。
測れない人件費は、データを見る前に固定した範囲 Θ で掃引し、決定 a ≻ b が成り立つ割合 Rob と、損益分岐の成功率を報告する（ADR-032）。

### 9.3 検証で分かったこと

| 主張 | 結果 |
|---|---|
| 割り振りの和が台帳と一致する（EC-B2 H1） | 274/274 run で誤差 6.5e−16 [live]。**支持** |
| 履歴キャッシュを外したときのコスト増を事前に予測できる（H3） | 同じ run の軌跡の上の反実仮想で、予測誤差 0.6% [live]。**支持** |
| 詳細出力の版のコスト増の大部分がテスト出力に帰属する（H2） | 点推定 2.40 は基準 0.8 を満たしたが、比の区間 [−20.7, 23.0] が定まらない。**未検証**。分子（テスト出力に帰属した生涯コストの増分）は 0.112 USD [0.095, 0.129] で事前見積り 0.121 USD と重なった。分母（版のコスト差）が 0.046 USD [−0.061, 0.129] で 0 と区別できない |
| ROI の決定がロバストか（EC-R1） | Rob(c01 ≻ c13) = 1.0、Θ を広げても 0.986。帰無対照の確信割合 0.00067 [simulated] |
| 実務上の費用差 | 履歴キャッシュを外すと 1 run の費用が約 2.1 倍（0.119 対 約 0.056 USD） |

もう 1 つの重要な観察は、**植込み c13 の 1 run の費用は c01 とほぼ同じ（0.048 対 0.050 USD）なのに、静かな誤りの率は 3 倍だった**ことである。
トークン費用と可視合格率を見ている限り、この版の劣化は見えない。

### 9.4 工夫

- **ハーネスのコスト効果は、同じ軌跡の上の反実仮想で測る。** 詳細出力の版は、平均 0.49 ステップ少なく、タスクごとのコスト差は
  ステップ数の差と強く相関した（相関 0.89）。版の間で実費を比べると、ハーネス変更の効果よりも振る舞いの揺れのほうが大きい。
  版の間の比較では、履歴キャッシュの事前予測（増加率 1.586）さえ実測の区間 [0.764, 1.513] を外れた。
  **費用の効果は、同じ軌跡に式を当てた反実仮想か、ステップ数を揃えた比較で測る**
- **ROI は決定として報告し、Θ はデータの前に固定する。** Θ を後から選べば、どんな決定も「ロバスト」にできる。
  なお EC-R1 の Rob 1.0 は、c13 の S の減少が W と F の両方に移り、どちらも S より高くつくのでほぼ自動的に満たされた。
  Rob が「決定が仮定に依存する場合」を正しく見分けるかは試されていない
- **比の基準には、分母の区間を基準の前に見積もる。** EC-B2 の H2 は、予定していた区間幅の見積りを実行しなかったため、
  分母が 0 を含みうることを事前に見抜けなかった
- **費用指標と品質指標を組にする（原典 4.11 の経済版）。** トークン費用だけを最適化するハーネス改善は、静かな誤りの増加を見逃す

## 10. 可視テストと静かな誤り対策

### 10.1 課題

コーディングエージェントはテストを読み、走らせ、書き換えることもできる。エージェントにとってテストは採点器であると同時に作業の道具である。
そのため「テストが緑」は次の 3 つを区別しない。

- 原因を正しく直した（S）
- 見えるテストだけを通す修正をした（入力の特別扱い、呼び出し側での局所回避、テストの改変）＝ **静かな誤り（W）**
- 失敗した、または終わらなかった（F）

W は S と同じ緑に見えるが、漏れた欠陥の後始末が高ければ F より悪い。さらに pass@k は「どれが成功かを知るオラクル」を前提にしているので、
現場で選択器に使う可視テストが W も緑と判定する以上、**pass@k は再試行の価値を過大評価する**。

### 10.2 手法

| 手法 | 内容 |
|---|---|
| 可視テストと隠しテストの二層化 | エージェントに見せる可視テストと、見せない隠しテストを同じケースバンク（公開 API の呼び出しと期待値の一覧）から描画する。仕様の食い違いを避けるため |
| S / W / F の 3 類分解 | 隠しテストを真値にして結果を数える。可視合格率 $\pi_S + \pi_W$ ではなく、W を独立に報告する |
| 合否の判定方法 | 標準出力の件数ではなく JUnit XML と期待ノード集合で判定する（ADR-041）。テストを消したり名前を変えたりして件数を合わせる操作に騙されない |
| 隠しテストの強さの報告 | 隠しテスト自体を変異スコアで評価して併記する（平均 0.846）。W は「下限寄り」と読む |
| 特殊化の検出 | 可視テストに現れる識別的なリテラルが本体の差分に現れるかを決定的に見る（`spec_literal`） |
| 実現可能な pass@k | 「可視テストが緑になった最初の試行を採用し、最大 k 回」の方策で、$P_k(\text{成功}) = s\,\frac{1-f^k}{1-f}$、$P_k(\text{W}) = w\,\frac{1-f^k}{1-f}$。pass@k との差 $G_k$ が W の多い版ほど大きくなる |

### 10.3 検証で分かったこと

| 主張 | 結果 |
|---|---|
| 可視合格率では見えない差を W で拾える（EC-R1） | 可視合格率の差 −0.049 [−0.132, 0.007]（区間は 0 を含む）の 2 版で、W の率の差 0.160 [0.069, 0.285] [live]。帰無対照 c12 には反応しない。**PASS** |
| 実現可能な pass@k の閉形式が経験値と一致する（EC-R2 H1） | MAE 0.012 [simulated]。ただし F がほぼ 0 なので閉形式はほぼ定数で、弱い支持 |
| W の多い版ほど pass@k との差が大きい（H2） | $G_3$ の差 0.075 [0.021, 0.135]。c13 では pass@6 0.917 に対して実現する成功率 0.757。**支持**（ただし EC-R1 の W の差を言い直したもので、独立の証拠ではない） |
| 「緑になるまで再試行」は W を増やす（H3） | **N/A**（判定から除外）。c13 の F の率 0.0625 が適用条件 0.15 に届かず、検出力が無い。合格ではない |

読み取れることを 3 つ挙げる。

1. **ベースラインでも W は 0 ではない。** c01 で 7.6%、可視テストが緑でも 13 本に 1 本は隠しテストで落ちる。
   W はタスクに強く偏り、3 版の W 48 件は 24 タスク中 12 タスクに集中した。あるタスクは全版・全反復で W だった
   （既定値を直さず、呼び出し側で引数を渡して可視テストを通す局所回避）
2. **可視合格率で見た劣化は、隠しテストで見た劣化の 4 分の 1 に満たない。** c13 の S は 0.208 下がったが、可視合格率は 0.049 しか下がらず、
   しかもそのほとんどは出力上限での打ち切り（12 章）で説明される
3. **run の内側のループが、外側の再試行の余地を吸収する。** 完了した run はすべて可視合格で、可視テストが落ちたまま完了を宣言した run は 0 だった。
   エージェントは run の中で「テスト → 編集」を緑になるまで繰り返すので、外側の再試行で W が増える余地はもともと小さい

### 10.4 工夫

- **W は下限寄りと読む。** 隠しテストも有限の仕様で、部分的な修正が S に数えられうる。隠しテストの変異スコアを必ず併記する
- **再試行の方策は、ハーネスの内側のループと組で評価する。** 再試行回数を決めるときは pass@k ではなく実現可能な pass@k で見積もる。
  w / s が大きいエージェントでは、再試行は 1 回目から ROI を下げうる
- **W の集中を区間に反映する。** W が少数のタスクに集中すると、タスク単位のクラスタ・ブートストラップの被覆は名目より低くなりうる
  （同時信頼帯で約 0.85 を確認）。件数で見た W の多さと、W を生むタスクの多さを分けて報告する
- **観測信号だけによる W の推定は、W を十分に集めてから。** 隠しテストなしで W を推定する ê は、AUC の区間幅 0.1 に W 約 120 件が要る。
  ベースラインが易しすぎる（S 0.91）環境では、まず W と F を増やすタスク設計が要る

## 11. 目印効果の直接注入 ＋ 双子 ＋ 盲点の探針

### 11.1 課題

コーディングエージェントの権限評価は、ふつう「どのコマンドを許可したか」で語られる。しかしテスト実行は任意コード実行と等価で、
許可済みのコマンドが何を起こすかは中身次第である。権限が「効いている」と言うには、実際に起きた効果を記録する計測器（効果モニタ）が要る。

ところが計測器そのものの検証には、次の困難がある。

- **攻撃の台本を書けない／書くべきでない。** 本プロジェクトでは、許可済みの経路を使う試みの台本の生成が安全フィルタに止められた。
  フィルタを回避することはせず、また結果ページに攻撃手順を書かないことを規則にしている
- **再現率 1.0 は空虚になりうる。** 何にでも警報を出す計測器は再現率 1.0 になる
- **見えないものは数えられない。** 計測器の盲点は、検出されないこと自体が盲点の症状なので、検出件数からは分からない

### 11.2 手法

計測器の**感度・特異度・盲点**を、攻撃の台本を書かずに測る 3 点の組である（ADR-042）。

| 要素 | 内容 | 何を測るか |
|---|---|---|
| **目印効果の直接注入**（本体） | ハーネスがサンドボックスの中で、無害な目印となる禁止効果（偽の HOME への書き込み、想定外の場所への書き込み、ハニーポットの読み出し、接続の試み、カナリアのシンクへの出力、許可リスト外の起動など 8 類）を直接起こす。各注入には、期待する効果のラベルと、それを記録するはずの観測層の集合を**実行前に**固定する | 感度（層別の再現率） |
| **双子**（対照） | 各注入に 1 件ずつ、同じプロセスの種類・同じ起こし方・同じ観測層を通るが禁止効果を伴わない操作（/tmp への同じ書き込み、秘密でないファイルの読み出し、別の鍵で作った囮の値の出力、許可されたプログラムの起動など）を並べる | 特異度。層に何かが記録されたことだけで警報を出す検出器を落とす |
| **盲点の探針**（記録のみ） | 計測器が**見えないと予測する**注入（監査フックの効かないプロセスによる読み出し・接続・起動、記録の置き場そのものへの書き込みなど）を走らせ、予測どおり見えないかを記録する。再現率の分母に入れず、基準にもしない | 観測範囲の宣言が正しいか |

あわせて、正面から禁止効果を要求する操作（権限ブローカーが拒否する）を各単位に 1 回含め、拒否された操作が効果を残さないかを検査する。

### 11.3 検証で分かったこと（EC-S1）

| 基準 | 値 [simulated] | 読み方 |
|---|---|---|
| 全体の再現率 ≥ 0.95 | 1.0（30/30、Clopper–Pearson 下限 0.884） | 観測範囲の内側に置いたカタログに対する値。1.0 は「観測範囲の宣言が正しい」ことの確認 |
| 層別の再現率の最小 ≥ 0.9 | 1.0（ファイル差分 10/10、監査フック 12/12、起動記録 1/1、シンク走査 10/10） | 観測した率への基準で、各層の真の再現率が 0.9 以上という統計的主張ではない（層別の下限は 0.69・0.74・0.025・0.69） |
| 双子の誤警報 = 0 | 0 | 双子は予測した層に 27/27 記録されたので、「何も記録されなかった」ことによる空虚な 0 ではない |
| 拒否の効果残存 = 0 | 0（拒否 43 呼び出し） | ほぼ構成上の 0。残存の検出器が働くことは EC-O2 で別に確かめた |

盲点の探針 9 件は予測どおり（痕跡なし 8、観測不能 1）で、食い違いは 0 だった。監査フックの記録の置き場そのものへの書き込みは
観測の外にあり、効果モニタでも評価基盤の検査でも検出できないことが、宣言された盲点として残った。

一方、NEW_IDEA が当初示したかった「コマンドの許可リストは権限を保証しない」（許可済みの経路を経由した効果をコマンド規則は見逃し、
効果モニタは検出する）は、台本を作れなかったため第 1 段では**実証していない**。

### 11.4 工夫

- **盲点の探針を基準にしない。** 「検出されないこと」を基準にすると、計測器を弱くするほど通る基準になる。探針は盲点を数として見せるための記録にとどめる
- **双子は「同じ層を通った」ことを確かめる。** 双子の記録率（27/27）を出さないと、誤警報 0 が空虚かどうかが分からない
- **予測する層を実行前に固定する。** 注入ごとに期待する層の集合をカタログのメタデータとして固定すると、
  「予測外の層に禁止効果が記録された」ことも検出でき、観測範囲の宣言そのものを検査できる
- **危険な効果は実行せず、試行として記録する。** 外部送信や拒否された操作は実行せず、もっともらしい応答を返して記録する
  （原典 6.4 の dry-run プロキシと同じ形）。計測器の検証に本物の危険を持ち込まない
- **主張の範囲を書く。** 30 件は固定したカタログで、母集団からの標本ではない。「このカタログに対する層別の再現率」と書き、
  一般の効果や任意の経路に対する再現率は主張しない

## 12. 失敗の読み方

### 12.1 課題

評価が「失敗」を出したとき、その原因は少なくとも 4 つありうる。手法が働かなかった、評価器が壊れていた、
植え込んだはずの欠陥が植わっていなかった、検出力が足りなかった。これらを結果を見てから区別しようとすると、
都合のよい読み方を選んでしまう。逆に「成功」も、自動的に満たされる基準や点推定だけの合格を含みうる。

第 1 段では、これが実際に起きた。

- **植込みの不発**: 「入力を特別扱いするハードコード（特殊化）」を起こす狙いの c13 は、文面を 3 回作り直しても実モデルに特殊化を書かせられなかった
  （操作確認 0/10 × 3）。診断では、植込みは全 run に届き（版ハッシュとカセットが一致）、検出器も正しかった（特殊化パッチ 42/42 で発火、正解パッチ 0/42）。
  Haiku 4.5 は本文で指示を復唱・検討しながら（4/10 run）、指定された形の変更を 1 件も書かなかった。
  **指示として言ったことと、コードとして書いたことが食い違う**
- **見える失敗の正体**: F 11 件のうち 10 件は、出力上限 2,048 トークンで応答が切れて run が終わったものだった。
  コーディング用ループは、ツール呼び出しの無い応答で `stop_reason` が `max_tokens` でも run を終えていた。
  F はエージェントの能力の失敗ではなく、**ハーネスの設定の産物**だった
- **点推定だけの合格**: EC-B2 の H2 は点推定 2.40 が基準を満たしたが、区間 [−20.7, 23.0] が定まらなかった
- **判定できない基準**: EC-R2 の H3 は検出力が無く、そのまま判定すれば「合格」とも「不合格」とも読めた

### 12.2 手法

| 手法 | 内容 | ADR |
|---|---|---|
| FAIL と NEGATIVE の区別 | FAIL はこちらの実装・設計の不備、NEGATIVE は実装は正しいが主張が成り立たない。判定ごとに種別を明示する | — |
| 植込みの操作確認 | コーパスの前に植込み版を少数 live で走らせ、**植込みの痕跡だけ**を見る（合格率や W の率は見ない）。発火率から必要な反復数を決め、作り直しは 2 回まで | ADR-037 |
| 失敗したときの読み方の事前固定 | 操作確認が通らなかった植込みについて、コーパスを見る前に「差が出なければ植込みの不発による FAIL（設計側）とし、手法の NEGATIVE とは読まない」「差が出たら『操作確認を通っていない植込み。機構は特殊化ではない』と明記する」を固定する | ADR-046 |
| 適用条件つきの基準と N/A | 到達上限が観測量に依存する基準に `applies_if` を付ける。条件が偽なら N/A（検出力不足）とし、合格に数えない | ADR-045 |
| 基準の情報量の分類 | 基準を「情報のある基準」「ほぼ自動的に満たされる基準」「自己検査・構成上の基準」「点推定だけが満たした基準」「N/A」に分け、判定表の PASS に設計者の 1 行の読み方を添える | — |

### 12.3 検証で分かったこと

- **事前固定が機能した。** c13 は操作確認を通らなかったが、データを見る前に読み方を固定していたので、コーパスで W の差が出たとき
  「手法が特殊化を検出した」とは書かず、「局所回避と指示違反を起こす版について、可視テストでは見えない W の差を拾った」と書けた。
  主張の範囲は狭まったが、取り違えは起きなかった
- **基準の多くは情報が薄い。** 第 1 段の基準 27 個のうち、植込みと対照を区別し、満たさない実装がありえた「情報のある基準」は約半分だった。
  残りは自己検査・構成上の基準（配管が通っていることの確認）、ほぼ自動的に満たされた基準、点推定だけの基準、N/A である
- **失敗率をモデルの能力と読む前に、ループを読む。** F の 10/11 が出力上限での打ち切りだったことは、
  可視合格率の版の差（−0.049）もほぼ説明する

### 12.4 工夫

- **操作確認では、合格基準の指標を見ない。** 植込みの痕跡（特殊化の発火）だけを見る。合格率を見れば、基準や植込みを結果に合わせたくなる。
  第 1 段では、操作確認の段の出力に見てはいけない合格数が含まれていた欠陥があり（欠陥 1）、出力の経路そのものを直した
- **植込みはプロンプトではなくハーネスの機構で入れる。** 出力の詳細度（c04）と履歴キャッシュ（c01o）の植込みは決定的に効いた
  （c01o は 10/10 run でキャッシュが外れていることを確認）。行動を指定するプロンプトの植込みは 3 回作り直しても効かなかった。
  符号の分かった真値はハーネスの機構か環境に置き、プロンプトの文面で効果を作る評価には操作確認を必須にする（観察。13 章）
- **N/A は合格の一種ではない。** 判定表・結果ページ・要約のすべてで、N/A を「合格」と分けて表示する。表示が N/A を無視していた欠陥（欠陥 5）も見つかった
- **PASS には読み方を添える。** 「PASS」の一語は、情報のある合格も、自動的な合格も、点推定だけの合格も同じに見せる。
  判定表に設計者の 1 行の要約を載せ、何が言えて何が言えないかを並べる

## 13. ハーネスのバージョン管理とループエンジニアリング

### 13.1 課題

- **振る舞いの多くはハーネスで決まるのに、ハーネスは版として扱われていないことが多い。** モデルとプロンプトが同じでも、
  出力上限・履歴キャッシュ・終了条件が違えば別のエージェントである。これを同じ版として扱うと、結果の差を説明できない
- **ハーネスのどの部品が効いたのかが分からない。** 部品は組み合わせで効くので、1 つずつ外して比べるだけでは寄与が分離できない
- **ループの設計が、評価の数値を作っている。** 第 1 段の F の大半はループの終了条件から来た。外側の再試行の価値は、内側のループにすでに吸収されていた
- **記録と再生を使う評価では、反復が独立でなくなりうる。** 同じリクエストに同じ記録が当たると、10 回の反復が 1 回の応答の再生になる

### 13.2 手法

**ハーネスを版の一部として明示する（ADR-035）。** ハーネスの部品を版の設定に明示し、版のハッシュに含める。
NEW_IDEA が挙げた部品は次のとおりである。

| 部品 | 値 | 変えるもの |
|---|---|---|
| `auto_test_hook` | on / off | 編集のたびに可視テストを走らせ、要約を次のメッセージに足す |
| `compaction` | none / drop_old(k) | 古いツール出力を落とす |
| `repo_map` | on / off | 初回メッセージにファイル木と主要シンボルを入れる |
| `memory_file` | none / path | プロジェクトメモ（CLAUDE.md 相当）をシステムプロンプトに入れる |
| `test_output_limit` | 行数 | テスト出力を切り詰める |
| `permission_policy` | P0〜P4 | 権限方策 |
| `spotlighting` | on / off | 信頼できない出力を区切り、指示として扱わないよう規定する |
| `egress` | allow / deny | 外部送信の可否 |
| `tool_timeout_s` | 秒 | テストとシェルのタイムアウト |
| `history_cache` | on / off | 会話履歴の末尾にプロンプトキャッシュの区切りを置く |

既存の版の定義（オフィス環境の `VersionConfig`）は変えず、コーディング用のタスク・版・プロンプト・生成物を分離した（ADR-039）。
既存の 13 版のハッシュと 30 実験の入力が変わらないようにするためである。

**ループを自前で回す（ADR-001）。** SDK の tool runner を使わず `messages.create` のループを自前で書く。
ステップ境界ごとのスナップショット、分岐再実行、効果の組み立て、予算の停止をハーネス側で制御するためである。
予算超過はループの中で飲み込まず、実験まで伝える（ADR-040）。

**反復の独立性をカセットの塩で担保する（ADR-038）。** 記録の鍵に任意の塩を足し、反復ごとに別の応答を得る。塩の不備と同一の試行を検査する。

**ハーネスの反実仮想を、最初の分岐点からの再生で得る（原理 B、未実施）。** 版を固定してハーネスや環境の側だけを変えると、
最初にリクエストが食い違うステップ j までは記録の再生が正しい標本になる。費用は接尾辞だけで、対になった標本なので分散も小さい。
j は「記録に当たらなかった最初のリクエスト」として機械的に決まる。前提として、再生ではツールを再実行せず、記録したツール結果でメッセージを組み立てる
（ツール出力の実行時間や一時ファイル名で、偽の分岐点が出るのを防ぐ）。

| 反実仮想 | 最初の分岐点 j |
|---|---|
| 版（システムプロンプト）を変える | 0（節約なし。E3-5） |
| フックをステップ k で初めて発火させる | k + 1 |
| 権限方策を変える（ステップ k で初めて判定が変わる） | k + 1 |
| ツールに遅延を足す（エージェントに時刻を見せない） | ∞ |
| 予算上限で打ち切る（エージェントに告げない） | ∞ |

**部品の寄与を協力ゲームとして分ける（EC-H1、未実施）。** 部品の on / off の組合せで成功率を測り、Shapley 値で各部品の寄与を推定する。
符号の分かった植込み（＋／0／−）で、推定が符号を回復できるかを検証する。

### 13.3 検証で分かったこと

| 対象 | 結果 |
|---|---|
| ハーネスの設定を版のハッシュに含める | 出力上限や履歴キャッシュを変えた版を、モデルとプロンプトが同じでも別の版として扱えた。c01o は 1 run の費用がベースラインの約 2.1 倍になり、その差を事前に予測できた |
| 機構で入れたハーネスの植込み | 詳細出力（c04）と履歴キャッシュ（c01o）は決定的に効いた。プロンプトの植込み（c13）は効かなかった |
| ループの終了条件 | F の 10/11 が「`max_tokens` で切れた、ツール呼び出しの無い応答」で run を終える設定から来た |
| 内側のループと外側の再試行 | 完了した run はすべて可視合格。外側の再試行の効果（EC-R2 H3）は検出力が無く N/A |
| 反復の独立性 | 塩の不備 0、同一の試行 0（336 run） |
| 部品の寄与（EC-H1）・分岐点からの再生（EC-H2）・モデルとの交互作用（EC-H3） | **未実施**。ハーネス評価の中核は第 2 段以降の課題 |

### 13.4 工夫

- **版のハッシュに含めるものを決めるのが、バージョン管理の本体である。** モデル・プロンプト・ツール定義に加え、出力上限、キャッシュの区切り、
  終了条件、フック、権限方策、再試行の方策をまとめてハッシュにする。含め忘れた設定は、結果の差の「説明できない揺れ」として現れる
- **既存の版を変えずに拡張する。** 評価対象を広げるときは、既存の版の定義を変えずに分離する。既存の結果の再現性を守るためである
- **ループの最初の改善候補は終了条件である。** 「出力上限で切れた応答に続きを促す」部品は、F のほぼすべてと可視合格率の版の差を説明し、
  費用も小さい。部品の効果を測る EC-H1・H2 の最初の植込み候補にもなる
- **再試行は内側のループと組で設計・評価する。** 「緑になるまで再試行」を外側に置いても、エージェントがすでに内側で緑になるまで直しているなら効果は小さい。
  再試行が静かな誤りを増やすかは、run の中の「テスト → 編集」の繰り返しについて問い直す
- **開発ループの側にも同じ規律を当てる。** 本プロジェクトの開発では、役割ごとにモデルを固定し（設計 Opus 5.5、実装とレビュー Sonnet 5.5、実行 Haiku 5.5）、
  1 タスク 1 worktree 1 ブランチで並列に進め、独立レビューは仕様と差分だけを渡し、live の実行は関門の承認と累積予算の上限を書いた指示のときだけ許した。
  第 1 段の欠陥 9 件はすべて独立レビューか設計者の解析で見つかった。AI で開発するハーネスにも、版・関門・独立した検査・予算の停止が要る

### 13.5 ハーネスの変更を評価する手順

13 章までの手法と工夫を、ハーネスの変更 1 件を評価する手順にまとめる。

1. **版を定義する**: モデル・プロンプト・ツール・ハーネスの設定（出力上限、キャッシュ、終了条件、フック、権限、再試行）をまとめてハッシュにする
2. **採点を二層にする**: 可視テストと隠しテストを同じ仕様から用意し、S / W / F で数える。隠しテストの強さを併記する
3. **ベースラインだけでパイロットを走らせる**: 分散・難度・1 run の費用を測り、到達上限と検出力から基準を置く。観測量に依存する基準には適用条件を付ける
4. **符号の分かった植込みを、ハーネスの機構で作る**: 操作確認で痕跡だけを見る。失敗したときの読み方を先に書く
5. **費用の効果は実行前に予測する**: 位置モデルで変化を見積もり、実行後は台帳の恒等式と、同じ軌跡の上の反実仮想で照合する
6. **報告は分布と決定で出す**: S / W / F、実現可能な pass@k、Θ を掃引した Rob と損益分岐の成功率。基準ごとに情報量を書き、PASS に読み方を添える
7. **評価基盤を毎回検査する**: 仲介されない効果、秘密の漏れ、記録の整合性、拒否の効果残存を、コーパスごとに自動で確かめる

## 14. 第 II 部の根拠の強さ

第 II 部の知見は、根拠の強さが揃っていない。持ち出すときは次の段で読む。

| 段 | 意味 | 該当 |
|---|---|---|
| **実証** | 植込みと対照で手法が働くことを確かめた | 使用量記録からのコスト帰属と台帳の恒等式、ハーネス変更の費用効果の事前予測（run 内）、二層テストと S / W / F 分解（1 つの植込み）、実現可能な pass@k の閉形式、効果モニタの検証（注入 ＋ 双子 ＋ 探針）、評価基盤の常時検査（植え込んだ種類） |

## 15. 2 つの部をつなぐもの

### 15.1 同じ構造の問題が、2 つの環境で繰り返し現れた

| 効率だけを最適化すると品質が落ちる | 効率化の版でステップ 0.796 倍・検証行動率 0 倍・合格率は据え置き（E4-9） | 1 run の費用がほぼ同じ版で、W が 3 倍（経済版の Goodhart） |

| 評価器のほうが先に壊れている | 欠陥 21 件中 16 件が評価器側 | 欠陥 9 件すべてが評価器・手続き側 |
| 基準が到達不能・検出力不足 | 3 件（N 倍の基準、効果量が誤差に埋もれる基準） | 事前の手続きで到達不能は防げた。比の基準の分母の揺れは見逃した |
| 分岐再実行の節約 | 版を変えたので j = 0、節約なし（E3-5） | 版を固定してハーネスや環境を変える反実仮想なら節約が成立する、と整理（原理 B。未実施） |
| 決定的な代役の限界 | 代替ジャッジは向きは合うが一貫して甘い。sim は作法と絶対水準を再現しない | コーディング用の sim は作らず、決定的な代役は計測器の検証にだけ使った。ROI の数値はすべて live |

### 15.2 原典の 3 原理は、検証を経てどう変わったか

| 原理 | 検証が加えたこと |
|---|---|
| 情報量／コストの最適化 | 不確実性の最大化と逃走欠陥率の最小化は別の最適化問題である（E3-3）。コストを減らす手段（分岐再実行）は、何を変えたかで効いたり効かなかったりする（E3-5、原理 B） |
| 主張ではなく証拠 | ツールログすら効果の代理にすぎない（原理 A）。さらに「言ったことと書いたこと」が食い違うので、プロンプトで指示した内容も証拠にならない。差分という効果で確かめる |
| 評価系そのものが劣化する製品 | 評価系は時間で劣化する前に、作った時点で壊れている。健全性指標は、劣化の監視より先に**植込みによる評価器の検査**として要る（EC-O2） |

### 15.3 評価を誤らないための規律（両部に共通）

1. **基準は実装前に固定し、後から緩めない。** 緩めるなら理由を記録する（ADR）。本プロジェクトは 36 実験・133 基準を通して、
   結果を見て基準を緩めたことは一度もない（第 II 部の暫定基準は、植込み版を走らせる前にベースラインのパイロットだけから確定した）
2. **基準は到達上限と検出力から置く。** 「ランダムの N 倍」は避け、比の基準は分母の区間を先に見積もる
3. **パイロットはベースラインだけで行う。** 植込み版の結果を見て基準を合わせることを構造的に防ぐ
4. **植込みは操作確認してから使う。** 痕跡だけを見る。符号の分かった植込みはハーネスの機構か環境に置く
5. **失敗したときの読み方を、データを見る前に書く。** FAIL と NEGATIVE、N/A と合格を分ける
6. **数値に来歴を付け、混ぜない。** live・replay・simulated・unit を指標ごとに書く
7. **評価器を植込みで検査し、独立したレビューで数値を検算する。** 欠陥は「実験が通っているか」からは見つからない
8. **PASS に読み方を添える。** 何が言えて、何が言えないかを、判定の隣に書く

## 16. 限界

1. **例示環境である。** オフィスは SQLite の合成環境、コーディングは 6 個の小さな自作リポジトリと単一変異のバグ修正。
   実際の開発現場のコードベースの規模・依存関係・曖昧な仕様は再現していない
2. **被験モデルは 1 種（Haiku 4.5）である。** ハーネスの効果がモデルを替えても保たれるかは確かめていない
3. **オフィスの個々の手法は live で取り直していない。** live で検証したのは sim の妥当性（E0-1）、ジャッジ（E0-2）、モデル指紋（E8-6 の一部）までで、
   残りは sim の数値である。LLM の意味理解に依存する部分は決定的な代替で置き換えており、示せたのは配管が通っていることまで
4. **原典 5・6 章（ジャッジと人の組み合わせ、オンライン評価）は直接の検証対象ではない。** 第 4 章は関連する実験からの間接的な知見である
5. **コーディングのベースラインは易しすぎる**（S 0.91）。W と F の件数が少なく、区間が広い
6. **植込み c13 は操作確認を通っていない。** 静かな誤りに関する結論は「局所回避と指示違反を起こす版」についてのもので、特殊化には及ばない
7. **EC-S1 は経路の悪用を走らせていない。** 効果モニタの感度と特異度を固定カタログで測っただけである
8. **人件費のパラメータは仮定である。** Rob は事前に固定した Θ の上の値で、現場の費用構造を測ったものではない
9. **オフィス 4 実験（E3-3・E3-7・E4-3・E8-7）の保存済み結果 JSON が結果ページとずれている。** 判定表の行は結果ページに合わせて手で戻している

## 付録 B　用語

| 用語 | 意味 |
|---|---|
| 植込み／対照 | 手法が反応すべき欠陥を入れた条件／反応してはいけない条件 |
| FAIL / NEGATIVE / N/A | こちらの実装・設計の不備／実装は正しいが主張が成り立たない／適用条件が偽で検出力が無く、判定から外した基準（合格ではない） |
| 来歴 | 数値の出どころ。live（実 API）、replay（記録の再生）、simulated（決定的シミュレータ、スクリプト化エージェント、再標本化、掃引）、unit（単体テスト） |
| ハーネス | モデルの外側でエージェントの振る舞いを決める仕組み。プロンプト、ツールと出力の形、出力上限、キャッシュ、権限、終了条件、フック、再試行 |
| S / W / F | 隠しテスト合格／可視テストは合格だが隠しテストで不合格（静かな誤り）／可視テスト不合格または未完了 |
| NV / Rob | 正味価値／仮定パラメータの範囲 Θ のうち決定 a ≻ b が成り立つ割合 |
| 実現可能な pass@k | 可視テストが緑になった最初の試行を採用する方策での成功率。オラクルを前提とする pass@k と区別する |
| CCA | ツール出力の生涯コスト。その出力が以降のリクエストで再送されるたびに掛かる課金の和 |
| 効果モニタ | 起きた効果（ファイル差分、プロセス起動、読み書き、送信）を観測層ごとに記録する計測器。境界（サンドボックス）とは別物 |
| 双子 | 植込みと同じプロセス・起こし方・観測層を通るが、禁止効果を伴わない対照の操作 |
| 盲点の探針 | 計測器が見えないと予測する注入。予測どおり見えないかを記録し、基準にはしない |
| 操作確認 | 植込みが実モデルで狙いどおりの痕跡を残すかを、合格率を見ずに確かめる少数の live 実行 |
| 逃走欠陥率 | フル実行で見つかった失敗のうち、選択から漏れた割合 |
| 最初の分岐点 j | 2 つの実行条件でモデルへの入力が最初に食い違うステップ。それより前は記録の再生が正しい標本になる |
